## 2. 数值：CP、能力值、等级

### 2.1 等级与 CPM
- 等级 1 到 55，步长 0.5，共 109 个 CPM 值。PvPoke 直接查表，半级也在表里。
- 来源：`pokemon/Pokemon.js` 第 24 行 `cpms` 数组，`getCPMByLevel`（第 2026 行）。
- 状态：**参考 PvPoke**（1–51 级的值与游戏公开数据一致；51 级以上未独立核对）。
- 默认等级上限 50（`Battle.js` 第 11 行 `levelCap = 50`）。

### 2.2 实际能力值
```
攻击 = CPM × (种族攻击 + 攻击IV)          不取整
防御 = CPM × (种族防御 + 防御IV)          不取整
HP   = max(floor(CPM × (种族HP + HP IV)), 10)
```
- 来源：`Pokemon.js` `initialize`，第 380–382 行附近。
- 状态：**参考 PvPoke**。攻防保留小数这一点会影响伤害的断点，所以单独写明。
- 特例：脱壳忍者（dex 292）HP 固定为 10。

### 2.3 CP
```
CP = max(floor((攻+IV) × sqrt(防+IV) × sqrt(HP+IV) × CPM² / 10), 10)
```
- 来源：`Pokemon.js` `calculateCP`（第 425 行）；最低 10 在 `initialize` 里。
- 状态：**已验证**（见 `tests/test_stats.py`，与游戏内已知 CP 一致）。

### 2.4 联盟默认等级和 IV
- gamemaster 每只宝可梦有 `defaultIVs`，例如 `"cp1500": [等级, 攻IV, 防IV, HP IV]`。PvPoke 默认用这组值（`Pokemon.js` `initialize` 的 `"gamemaster"` 分支）。
- 无上限联盟（CP 10000）：15/15/15，等级取上限。
- 状态：**参考 PvPoke**。这是 PvPoke 的默认选择，不是游戏规则。

### 2.5 正作能力值换算（用于未发布宝可梦）
公式见 CLAUDE.md，已实现在 `pogo_sim/conversion.py`。
- 状态：**已验证**。11 只非 Mega（含 5 只触发 0.91 削弱的）和 50 只 Mega（含 5 只触发 0.97 削弱的）的换算结果与 gamemaster 完全一致。见 `tests/test_conversion.py`。
- 实现细节一：四舍五入用"0.5 进位"，不能用 Python 内置的 `round`（它是银行家舍入，遇到 .5 会出错，例如 Mega 超梦Y 的防御中间值 202.5）。
- 实现细节二：**削弱倍率要乘在最后一次取整之前**，不是对取整后的种族值再乘。CLAUDE.md 写的"三项乘 0.91"没有区分这两种做法，对照数据后确定是前者：
  - 请假王防御：round(174 × 1.05 × 0.91) = 166（游戏值）；先取整再乘会得到 167。
  - 雷吉奇卡斯 HP：round((1.75 × 110 + 50) × 0.91) = 221（游戏值）；先向下取整再乘会得到 220。

**两条削弱规则**（都按"只套公式的结果在 15/15/15、40 级的 CP"判断）：

| 适用 | 门槛 | 倍率 | 状态 |
|---|---|---|---|
| 非 Mega | CP ≥ 4000 | 0.91 | 已验证 |
| Mega / 原始回归 | CP ≥ 6000 | 0.97 | 倍率已验证；门槛待确认（数据只能限定在 5425–6039 之间） |

- Mega 削弱的依据：用户确认 Mega 超梦X/Y、Mega 烈空坐、原始固拉多/盖欧卡在游戏里都是 0.97 倍（2026-11-17 答复 Q2）。PvPoke 数据里恰好是这 5 只乘了 0.97，CP 最高的不削弱者是 Mega 烈咬陆鲨（5424），最低的削弱者是 Mega 烈空坐（6039）。
- 不是按"是否传说"划分：Mega 拉帝亚斯 / 拉帝欧斯（传说，4801 / 5007）和 Mega 蒂安希（幻之，4346）都没有削弱。
- 门槛是 `pogo_sim/conversion.py` 里的 `MEGA_NERF`，可以传自己的 `NerfRule` 试别的假设。将来出现 CP 落在 5425–6039 之间的新 Mega，就能定下准确门槛。
- Mega 超梦X：只套公式 412/222/235，削弱后 399/215/228（游戏值）。

## 3. 伤害

### 3.1 公式
```
伤害 = floor(0.5 × 威力 × (攻击/防御) × STAB × 克制倍率 × PvP加成 × [Mega招式加成] × [蓄力比例]) + 1
```
- 来源：`battle/DamageCalculator.js` `damage`（第 68 行）。
- 状态：**参考 PvPoke**，公式本身与社区公认一致。实现在 `pogo_sim/damage.py`，已用 PvPoke 源码逐位核对（见 3.6）。
- 乘法顺序照搬 PvPoke：`威力 × STAB × (攻/防) × 克制 × 蓄力 × Mega加成 × 0.5 × PvP加成`。浮点乘法不满足结合律，理论上换顺序可能在取整边界上差 1；实际搜索 40 万个随机组合没有找到这样的例子，但仍保持一致。

### 3.2 各倍率
| 倍率 | PvPoke 的值 | 说明 |
|---|---|---|
| PvP 加成 | 1.2999999523162842 | 即 float32 的 1.3 |
| STAB | 1.2000000476837158 | float32 的 1.2 |
| 效果绝佳 | 1.600000023841858 | float32 的 1.6 |
| 效果不好 | 0.625 | |
| 无效（双重抵抗同值） | 0.390625 | |
| 暗影攻击 | 1.2 | 乘在攻击上 |
| 暗影防御 | 0.83333331 | 乘在防御上 |
| Mega 招式加成 | 1 / 1.1 / 1.2 / 1.3 | 对应 Mega 等级 1–4，只对标记 `isMegaMove` 的招式生效，见第 7 节 |

- 来源：`DamageCalculator.js` 第 2–11 行 `DamageMultiplier`。
- 状态：**参考 PvPoke**。PvPoke 特意用 float32 精度的常数（2025-05 的两次提交 "fix: damage constant floating points"），说明这些精度会影响边界情况下的取整，我们照搬。
- 双属性：两个属性的倍率相乘（`getEffectiveness`，第 140 行）。

### 3.3 攻击和防御用什么值
```
有效攻击 = 攻击 × (能力等级倍率 × 暗影攻击倍率)
有效防御 = 防御 × (能力等级倍率 × 暗影防御倍率)
```
（PvPoke 先把两个倍率相乘，再乘到能力值上。）
- 暗影宝可梦在 gamemaster 里是单独的条目（如 `azumarill_shadow`，带 `shadow` 标签），PvPoke 据标签设置暗影倍率（`Pokemon.js` 第 406 行）。
- 来源：`Pokemon.js` `getEffectiveStat`（第 2091 行）。
- 状态：**参考 PvPoke**。

### 3.4 被盾挡下
- 伤害变为 1（`Battle.js` 第 1199 行）。
- 状态：**参考 PvPoke**，与 CLAUDE.md 里"待确认"的说法一致。

### 3.5 蓄力比例
- 模拟模式固定为 1（满蓄力）。只有训练对战里玩家手动蓄力时才小于 1。
- 我们的引擎可以先固定为 1，留一个参数。

### 3.6 与 PvPoke 源码的核对
`tools/pvpoke_ref/` 在 Node 里运行 PvPoke 源码（commit `d02018e`），生成 `tests/fixtures/pvpoke_damage_reference.json`：
- CPM 表 109 项、属性克制 3078 项（18 种招式属性 × 171 种防守属性组合）：逐位相同。
- 伤害用例 428 个（28 个手挑 + 400 个随机）：CP、有效攻防、克制倍率、STAB、最终伤害全部逐位相同。
- 手挑用例覆盖：双重弱点/抵抗、免疫、免疫×弱点、暗影攻守、能力等级 ±4、Mega 等级 1–4、威力 0、51 级。
- 其中 4 个是"float32 边界"用例：如果把 1.3 / 1.2 / 1.6 换成精确值，这 4 个的伤害会差 1，说明照搬 float32 常数确实有影响。
- 反向检查：故意改错暗影倍率、能力等级公式、STAB、Mega 加成，分别有 190、253、171、3 个用例失败，说明这套用例能发现这类错误。

暂不支持（形态变化留到以后）：Gulp Missile（按对手最大 HP 百分比算伤害）、Aegislash 等 11 个有形态变化的宝可梦的特殊规则。

## 5. 回合结构与结算顺序

这一节是 PvPoke 现在的实现（`Battle.js` `step`，第 284–612 行）。与官方说明的逐条对比在 5.4。
本项目的实现在 `pogo_sim/battle.py`（以回合为单位，冷却记作"还要等几回合"，与 PvPoke 的毫秒一一对应），已用 PvPoke 源码逐回合核对，见 5.5。

### 5.1 一个回合里发生什么
1 回合 = 500ms。每回合按下面的顺序：

1. **冷却减少**：双方 `cooldown` 各减 500ms，最低 0。换人计时器同样减 500ms。
2. **决定行动**：对 `cooldown == 0` 的宝可梦，决定本回合行动（快招 / 大招 / 换人）。
   - 如果**上一回合有大招结算**，本回合只接受换人，其他行动直接丢弃（第 341 行）。
   - 快招：冷却加上招式时长，放入队列。
   - 大招：冷却加 500ms，放入队列。
   - 决定行动时双方都用回合开始时的状态，互相看不到对方本回合的选择。
3. **从队列取出本回合要结算的行动**（第 397–431 行）：
   - 快招：在它的**最后一个回合**结算。即 N 回合的快招在第 T 回合开始，则在第 T+N−1 回合结算。
   - 例外："漂浮"的快招：如果上一回合有大招结算，所有在更早回合开始、还没结算的快招都在本回合立刻结算。
   - 大招：在放入队列的当回合结算。
   - 换人：当回合结算。
4. **按优先级从高到低依次执行**（第 434 行）。优先级：

   | 行动 | 优先级 |
   |---|---|
   | 换人 | +20（如果是大招后的 0 回合换人，再 −40，排到最后） |
   | 大招 | +10；攻击高于对手再 +1 |
   | 快招 | 0 |

   模拟模式下双方基础优先级都是 0；优先级相同时保持原顺序（0 号在前）。
5. **执行时的有效性检查**（第 449–493 行）：
   - 快招：对手已倒下则无效；自己已被**大招**打倒则无效。被快招打倒不影响。
   - 大招：能量够才有效；如果双方攻击不同（有先后手），后手被对方大招打倒则无效。
   - 换人：冷却为 0 且换人计时器为 0，或自己已倒下。
6. **回合结束**：检查倒下。如果本回合有大招结算，双方冷却都设为 500ms（第 548 行）。

### 5.2 大招的时序
综合上面的规则，一次大招是这样的：

| 回合 | 发生什么 |
|---|---|
| T | 攻方决定放大招。大招伤害和效果在本回合结算，先于本回合的快招。 |
| T+1 | "空回合"。双方不能出新招。之前没结算完的快招（漂浮）在这里结算。可以 0 回合换人。 |
| T+2 | 恢复正常，双方都可以行动。 |

所以放一次大招占 2 个回合。8 月更新之前只占 1 个回合，这是新系统带来的主要变化。

**大招期间的快招（Sneak 和 Leak）**：
- 对手在 T 回合才开始的快招（不管几回合长），在 T+1 结算，然后对手在 T+2 就能自由行动。相当于白拿了这个快招剩余的时长。
- 对手在 T 之前开始、原本要在 T 之后才结算的快招，同样在 T+1 结算，剩余时长作废。
- 对手原本就该在 T 回合结算的快招，在 T 回合大招之后结算；如果它被这个大招打倒了，这个快招不生效。

### 5.3 同回合的各种情况
- **双方同回合快招结算**：都生效，包括其中一方（或双方）因此倒下。
- **双方同回合放大招**：攻击高的先结算。先手打倒后手，后手的大招不生效。攻击相同时双方的大招都生效，即使被打倒。
- **一方大招、一方快招同回合结算**：大招先。被大招打倒的一方，快招不生效。
- **自己本回合会被快招打倒，同时放大招**：大招先结算，所以大招照常生效。

### 5.5 与 PvPoke 源码的核对
`tools/pvpoke_ref/export_battle_reference.js` 在 Node 里运行 PvPoke（commit `d02018e`），生成 `tests/fixtures/pvpoke_battle_reference.json`：
1. 让 PvPoke 的 AI 模拟一场；
2. 用 PvPoke 自己的沙盒模式（`setSandboxMode(true)`）把这场转成剧本：哪一回合放哪个大招、守方开没开盾、概率性能力变化有没有触发。其余回合一律快招；
3. 按剧本重放并逐回合记录双方的 HP、能量、冷却、能力等级、盾数。脚本会检查重放结果与第 1 步完全相同（52 场全部相同），说明剧本完全决定了对战。

`tests/test_battle_pvpoke.py` 用同一个剧本驱动我们的引擎（`ScriptedPolicy`），比较每一回合的状态、每一次招式的伤害和开盾、最终评分、回合数和对战时间。

## 6. 盾、CMP、能力变化、换人

### 6.1 盾
- 每方 2 个（`pokemon/Player.js` 第 20 行）。3v3 中全队共用。
- 挡下后伤害为 1。
- **被挡下的大招，附带的能力变化仍然生效**，包括对对手的削弱。代码里有一段注释写着"挡下就不削弱"，但实际没有起作用（`Battle.js` 第 1231–1233 行把修正值设成了 0，等于什么都没做）。
- 状态：**参考 PvPoke**。挡盾后削弱仍生效这一点与我对游戏的了解一致，但请确认（Q6）。

### 6.2 CMP（同回合大招的先后）
- 比较的是**不含暗影加成、不含能力等级**的攻击（`stats.atk`，即 CPM × (种族值 + IV)）。来源：`Battle.js` 第 262、783 行。
- 攻击高者先手。
- 攻击相等：没有先后，双方大招都生效（`usePriority = false`）。
- 状态：攻击高者先手 **参考 PvPoke**；攻击相等的处理 **待确认 Q8**（用户印象是游戏里随机决定先后，与 PvPoke 不同）；比较时是否不含暗影和能力等级 **待确认**。
- 引擎里做成开关：`PvPoke 方式（双方都生效）` / `随机先后（可设种子）`，默认 PvPoke 方式，方便对照。

### 6.3 能力等级
- 攻击和防御各自 −4 到 +4 级（gamemaster `settings.maxBuffStages = 4`，`buffDivisor = 4`）。
- 倍率：等级 s > 0 时为 (4 + s) / 4；s ≤ 0 时为 4 / (4 − s)。即 4/8 到 8/4。
- 来源：`Pokemon.js` `getStatBuffMultiplier`（第 2113 行）、`applyStatBuffs`（第 2077 行）。
- 状态：**参考 PvPoke**，与 CLAUDE.md 一致。
- 招式数据：`buffs: [攻击变化, 防御变化]`，`buffTarget: self / opponent / both`，`buffApplyChance`。`both` 时用 `buffsSelf` 和 `buffsOpponent`。
- 换下场时能力等级清零（`Battle.js` 第 996 行）。
- **概率性效果**：PvPoke 模拟模式不掷骰子。每个概率招式有一个计数器，初始值等于概率（50% 的招式初始为 0），每用一次加上概率，计数器每跨过一个整数就触发一次（`Battle.js` 第 1408–1417 行，`Pokemon.js` `resetMoves`）。
  例：12.5% 的 Night Slash 在第 7 次使用时触发；50% 的招式在第 2 次触发；10% 的招式在第 10 次触发（初始 0.1，用 9 次后浮点累计是 0.9999999999999999，不到 1）。
  计数器只给大招建；快招的概率效果在这个模式下从不触发（目前数据里没有带效果的快招）。
  这是 PvPoke 为了让结果可复现做的简化。见 Q7。实现：`BattleRules.chance_effects`，另有 `"random"` 选项；剧本可以逐次指定。

### 6.4 换人
- 换人冷却：45 秒（`Player.js` 第 22 行 `switchTime = 45000`；2025-09-04 提交 "Updated switch timer"）。主动换人时开始计时，倒下后的换人不触发。
- 大招期间换人冷却照常走（用户实战经验，Q13）。所以以回合为单位的引擎需要一个参数"每次大招折算成几秒"，数值待实测，3v3 阶段再定。
- 主动换人花 1 回合，倒下后换人和大招后换人不花回合（见 5.4）。
- 倒下后玩家有选择时间（PvPoke 训练模式里是 13 秒超时）。
- 状态：**参考 PvPoke**。
- **重要**：PvPoke 的普通模拟（Battle 页面、排名、矩阵）是纯 1v1，完全没有换人。换人只存在于训练对战模式。
- 换人在回合里怎么结算、PvPoke 训练模式的细节、3v3 的各项决定：见第 13 节。

### 6.5 胜负判定
- PvPoke 的 1v1 模拟在任一方倒下时结束，或时间超过 240 秒。
- "时间"的算法：没有大招的回合 +0.5 秒；有大招的回合按大招小游戏计 10 秒，同回合的第二个大招再加 10 秒（有盾时的计法略有不同，见 `battle.py` 的 `_end_of_turn_ms`）。只用快招时第 481 回合超时。状态：大招期间对战计时继续走——已验证（用户实战经验，2026-11-18），与 PvPoke 的做法一致；每次大招具体计多少秒（10 秒）参考 PvPoke。
- 对战评分 = floor(500 × 对手损失HP比例 + 500 × 自己剩余HP比例)，高者胜（`Pokemon.js` `getBattleRating`，第 2134 行）。
- 这是 PvPoke 的评分方式，不是游戏规则。我们的引擎可以输出同样的评分，方便对比。
- 换个写法更好理解：设 r自己、r对手 是双方剩余 HP 占最大 HP 的比例，评分 = 500 + 500 × (r自己 − r对手)（再向下取整）。所以：
  - 双方评分加起来是 1000（取整可能差 1）；
  - 一方倒下时，赢家 = 500 + 500 × 自己剩余 HP 比例（大于 500），输家 = 500 × 打掉对手 HP 的比例（小于 500）。例如赢下来只剩 10/361 HP 是 513，残血险胜；剩一半 HP 是 750；没掉血是 1000；输家 143 表示倒下前打掉了对手 28.6% 的 HP；
  - 同一回合双方都倒下：都是 500，平局；
  - 超时：剩余 HP 比例高的一方大于 500；
  - 只看 HP，不看剩下的盾和能量（在 3v3 里这些也有价值，这里不算）。
- 九宫格（`pogo_sim/matchups.py`）：一对宝可梦在 0–2 盾对 0–2 盾九种组合下各打一场的评分，和 PvPoke 单场对战页面的盾数矩阵一样。PvPoke 排名里的 score 是另一套加权算法，我们没有做。

## 7. Mega

PvPoke 目前的做法（都是 **参考 PvPoke**，其中多项它自己也说是暂定）：

- gamemaster 里 Mega 有 `mega` 标签（64 只），其中 19 只还有 `supermega` 标签。
- **Mega 等级**：默认 3；有 `supermega` 标签的默认 4（`Pokemon.js` 第 63、146 行）。
- **第三个大招**：所有 Mega 都可以带（`hasThirdChargedMove`）。额外招式在 `extraChargedMoves` 里，是带 "+" 的专属招式（如 `DYNAMIC_PUNCH_PLUS`）。
  - "+" 招式共 19 个，其中 18 个标记了 `isMegaMove`；**`MOONBLAST_PLUS`（Mega 皮可西）没有标记**，所以 PvPoke 不给它 Mega 加成。疑似 PvPoke 数据遗漏，见 9.2。
  - `extraChargedMoves` 里还有 Cramorant 的 Gulp Missile（形态机制，不是第三个大招）。所以"能带第三个大招"要按"是 Mega 且有 `extraChargedMoves`"判断。

- **Mega 等级 4 的等级上限**：等级上限从 50 提到 52（`Pokemon.js` 第 294 行，2026-09-02 提交 "Mega Level 4 CP Boost"）。
- **CP 超上限的 Mega**：PvPoke 直接按 `defaultIVs` 用一个很低的等级（例如 Mega 超梦X 在 1500 联盟是 9 级），当成普通的低等级宝可梦处理。

- **每队几只 Mega**：PvPoke 的模拟是 1v1，不涉及；它的组队工具（`interface/TeamInterface.js` 第 817 行）在队里已有 Mega 时排除其他 Mega，即按每队 1 只处理。

用户 2026-11-17 的答复（Q9–Q11），本项目的做法：
- **Mega 等级 1–4 和专属招式加成是游戏正式机制**，照 PvPoke 实现。
- **等级上限做成可配置**，不写死 52。不同赛季规则不同，已知的有：Mega 等级上限固定 52；Mega 后自动提到 55；Mega 比普通上限多 2 级（加上挚友加成最高 53）。打算用"普通上限 + 挚友加成 + Mega 额外等级，或直接指定 Mega 上限"来表示。

- **CP 超上限的 Mega**：给定 IV，取不超过 CP 上限的最高等级，做成可配置。
- 另外，挑选让实际战斗力最大的 IV（按攻×防×HP 的乘积排名）是一个单独的功能，放在路线图第 2 步（自定义宝可梦）里做。已实现，见第 11 节。

用户 2026-11-18 的答复：
- **Mega 属性加成只在 Raid 生效，PvP 不生效**。Raid 里的数值是：与 Mega 同属性的招式 1.3 倍、其他属性 1.1 倍，作用于其他训练师的宝可梦，Mega 自己没有加成。引擎不实现这一项。
- **每队只能带 1 只 Mega**（正作基本也只允许一只）。3v3 组队时检查。
- 等级上限的几种赛季规则（固定 52、Mega 后 55、普通上限 + 挚友 + 2）**对所有 Mega 等级都生效，大师联盟也适用**。PvPoke 当前的做法不同：只有 Mega 等级 4 是 52，大师联盟仍是 50（`Pokemon.js` 第 294 行；`interface/PokeSelect.js` 第 347 行把 Mega 等级 4 的原形等级算作"Mega 等级 − 2"，说明它的 52 是"基础上限 50 + 2"）。

本项目的实现（第 2c 步，`pogo_sim/season.py`）：
- **赛季规则 `SeasonRules`**：普通等级上限（50）、挚友加成（1）、Mega 等级上限规则、CP 超上限的 Mega 是否自动降等级、每队最多几只 Mega（1）。
- **Mega 等级上限 `MegaLevelCap`**：要么直接指定上限（`fixed`），要么"普通上限 + 挚友加成 + `extra_levels`"；可以限定只对 Mega 等级 ≥ 某值生效、大师联盟是否适用。预设：

  | 预设 | 规则 | Mega 超梦X 在大师联盟（挚友） |
  |---|---|---|
  | `PVPOKE_SEASON`（默认） | Mega 等级 4 固定 52，大师联盟除外 | 51（挚友，按普通规则） |
  | `MEGA_CAP_52` | 所有 Mega 固定 52 | 52 |
  | `MEGA_CAP_55` | 所有 Mega 固定 55 | 55 |
  | `MEGA_PLUS_2` | 所有 Mega 为普通上限 + 2 | 53 |

  固定上限时挚友加成不另加。这里只管"上限"：不指定等级时，配置默认取上限内 CP 合法的最高等级，所以"上限 55"和"自动提到 55"在默认设置下结果一样。
- **按赛季建立配置 `season_build`**：不指定 IV 时用 IV 排名第 1（第 11 节）；不指定等级时用上限内 CP 合法的最高等级。CP 超上限的 Mega 自动降到合法的最高等级，不看 `levelFloor`、从 1 级起找（9.1）；普通宝可梦指定的等级超过 CP 上限时报错。怎么选出来的写在 `PokemonBuild.notes` 里，例如 Mega 雪妖女在超级联盟：

  ```
  赛季规则：PvPoke 兼容；超级联盟
  Mega 等级 4（默认）
  Mega 等级上限 52（适用条件：只限 Mega 等级 ≥ 4，大师联盟除外）
  IV 4/15/15：超级联盟 IV 排名第 1（能力值乘积最大；IV 下限 0，共 4096 个组合）
  等级 14.5：52 级时 CP 4187 超过 1500，自动降到 CP 不超过上限的最高等级（CP 1498）
  ```
- **第三个大招**：`make_combatant` 检查，只有带 `extraChargedMoves` 的 Mega 能带，而且第三个只能从 `extraChargedMoves` 里选（前两个不检查招式池，和以前一样）。gamemaster 里 64 只 Mega 中 19 只有（都是 supermega），其余 45 只现在最多两个大招。
- **每队 Mega 数**：`check_team` 检查，3v3 配置建队时用（13.8）。

完整流程（第 2d 步）：覆盖文件 → `season_build` → `make_combatant` → `Battle` + `SimplePolicy` → 文字报告（`pogo_sim/report.py`：双方配置和 `notes`、结果一行，再接 `format_timeline`）。用法见 README。

## 8. PvPoke 的 AI 策略

这一节是以后改进的重点，所以把假设写清楚。

PvPoke 有两套决策代码：
- `battle/actions/ActionLogic.js`：1v1 模拟用，完全确定性。排名、对战页面、矩阵都用它。
- `training/TrainingAI.js`：训练对战（3v3）用，带随机权重。换人只在这里。训练 AI 出招时最终也调用 `ActionLogic.decideAction`。

### 8.1 总的假设（最需要注意的）
1. **完全信息**：AI 知道对手的精确 HP、能量、招式、剩余盾数。
2. **防守方默认必开盾**：1v1 模拟里，只要还有盾就开，只有少数例外（见 8.2）。防守方不知道也不猜来的是哪个招式。
3. **因此骗盾必定成功**：攻方的"骗盾"逻辑建立在对手一定会开盾的基础上。
4. **攻方规划时不考虑对手会反击**：寻找最快击倒方案的搜索只看自己的能量和对手的 HP、盾，假设对手有盾就挡。
5. **只看 1v1**：模拟模式不考虑队伍里还有谁，不保留能量或盾给下一只。
6. **每只宝可梦有三个可调设置**（`Pokemon.js` 第 113–116 行）：
   - `baitShields`：0 不骗盾，1 选择性骗盾（默认），2 总是骗盾
   - `farmEnergy`：只用快招（默认关）
   - `optimizeMoveTiming`：优化出招时机（默认开）

### 8.2 什么时候开盾
来源：`Battle.js` `useMove` 第 1081–1262 行，`ActionLogic.wouldShield` 第 1164–1280 行。

默认：有盾就开。以下情况改用 `wouldShield` 的判断：
- 来的招式带"必定提升自己攻击"或"必定降低对手防御"的效果（如 Power-Up Punch、Acid Spray）。
- 防守方自己的最优大招会降低自己的防御（如 Close Combat）：
  - 攻方还有盾时，用 `wouldShield` 判断；
  - 攻方没盾时，只有当防守方的下一个大招周期能打倒攻方、且不会被攻方抢先时才用 `wouldShield`。
- 特定形态（盾形态坚盾剑怪、古月鸟的两个形态等）有专门规则。

`wouldShield` 的规则（满足任一条就开盾）：
1. 挨了这一下后的剩余 HP ≤ "周期伤害"。周期伤害 = (攻方攒下一个同样大招所需的快招数 + 1) × 快招伤害 + 1，再乘以防守方盾数。
2. 攻方**任意一个**大招（不管现在能量够不够）的伤害 ≥ 防守方当前 HP / 1.4，且攻方快招每回合伤害 > 1.5。
3. 攻方任意一个大招的伤害 ≥ 防守方当前 HP − 周期伤害。
4. 来的招式会降低攻方自己的攻击（如 Superpower），且伤害超过防守方当前 HP 的 55%。
5. 攻方设置为"总是骗盾"（`baitShields == 2`）时，直接返回"会开盾"。

注意第 2、3 条里有一个条件 `attacker.energy + chargedMove.energy >= chargedMove.energy`，它恒为真，所以实际上没有检查能量。这可能是 PvPoke 的笔误。

### 8.3 怎么决定放哪个大招、什么时候放
来源：`ActionLogic.decideAction`，第 6–1042 行。每当宝可梦可以行动（冷却为 0）时调用一次，返回大招或"用快招"。按顺序判断，前面命中就不往后走：

**第 0 步**：能量不够最便宜的大招，或设置了只用快招 → 快招。

**第 1 步：快死了就把能放的放掉**（第 38–208 行）
- 估算"还能活几回合"：假设对手照常出快招，我有盾时对手用最便宜的大招骗盾，我没盾时对手用任何能打倒我的大招。
- 如果活不到下一个快招打完（细分为几种情况，考虑 CMP 和对手快招时长）→ 放当前能放的伤害最高的大招。如果赢 CMP 且能量够同一个招放两次、两次总伤害更高，则选它。

**第 2 步：能直接打倒就打**（第 212–234 行）
- 对手没盾，某个大招能打倒对手，且这个招不会削弱自己 → 放。
- 但如果对手的 HP 低到一个快招就能打倒，则不放大招，用快招收掉。
- 设置了骗盾时，只考虑最便宜的那个招。

**第 3 步：特定宝可梦的规则**（谜拟Q、小陨星、古月鸟），略。

**第 4 步：优化出招时机**（第 267–373 行）
- 目的：让大招在对手快招刚打完的时候放，避免对手白拿回合。
- 做法：如果对手当前冷却为 0 或大于目标值（一般 500ms），就再打一个快招等一等。
- 不等的情况：双方快招时长相同；自己的快招时长是对手的整数倍；等的话能量会溢出 100；等的话会被打倒；现在就能打倒对手。

**第 5 步：对手还很耐打时，直接选"最优招"**（第 400–447 行）
- 条件：对手 HP / (最优大招伤害 + 攒它期间的快招伤害) > 2。
- "最优招"（`bestChargedMove`）主要按每点能量伤害（DPE）选，带一批针对具体招式的修正（`Pokemon.js` `resetMoves`，第 711–878 行）。
- 骗盾：如果设置了骗盾、对手有盾、且对手会对我的某个招开盾 → 改放最便宜的招。
- 选中的招会削弱自己时，先攒到接近 100 能量再连放。

**第 6 步：对手快倒了，搜索最快的击倒方案**（第 449–812 行）
- 状态：自己的能量、对手 HP、回合数、对手盾数、已用招式、攻击等级变化。
- 假设：对手有盾就挡（伤害记 1，盾数减 1）；每个大招占 1 回合（**没有按新系统改成 2 回合**）；概率性效果不计。
- 找到回合数最少的方案，取方案里的第一个招。

**第 7 步：对方案做一串修正**（第 814–1002 行）
- **骗盾**（设置了骗盾、对手有盾、自己有两个以上大招）：
  - 如果有一个更贵、DPE 更高的招现在能量还不够 → 先不放，继续用快招攒能量。攒够贵招的能量后，实际放的往往仍是便宜的那个。这就是 PvPoke 的"骗盾"：攒到对手无法从能量判断来的是哪个招，再用便宜招换盾。
  - 例外：便宜招本身必定提升攻击，且贵招的 DPE 不超过它的 1.5 倍 → 不骗。
  - 如果能量已经够贵招、贵招 DPE 超过 1.5 倍、且按 `wouldShield` 对手不会挡 → 直接放贵招。
- 不骗盾，或对手没盾且没有削弱自己的招 → 按伤害从高到低放。
- 之后是 6 条左右的"补丁"规则（代码里自己叫 bandaid），在能量相近时偏好 DPE 更高的、不削弱自己的、或必定提升自己的招。
- 会削弱自己的招：尽量攒到能连放再用；自己没盾且对手马上要放大招时，推迟到对手放完之后。

### 8.4 什么时候换人
只在训练对战里，来源：`TrainingAI.js` `evaluateMatchup`（第 633 行）、`decideAction`（第 1030 行）、`decideSwitch`（第 1131 行）。

**评估当前对位**：把当前这对宝可梦以当前的 HP、能量拿去跑 1v1 模拟，跑四种情形（双方骗盾 / 双方不骗 / 不骗 / 自己只攒能量），每种情形遍历双方各种盾数组合，按权重 [4, 4, 1]（对应 0、1、2 盾）加权平均，得到 0–1000 的评分，500 是平手。

**是否换人**（带随机）：
- 条件：有换人策略、换人计时器为 0、还有别的宝可梦。
- 换人权重 = (500 − 评分) / 10，评分越差越想换。高难度 AI 在对手还有多只时门槛降到 450。
- 对手被换人计时器锁住（剩余超过 30 秒）、且自己有更克制它的宝可梦时，加权重。
- 自己 HP ≤ 25% 时不换（高难度）。
- 高难度 AI 还有"攒完能量再换"：继续打快招，等到对手快要有威胁的大招时再换。
- 然后在"换人 / 默认 / 骗盾 / 攒能量"几个选项里**按权重随机抽一个**。

**换谁上**（带随机）：
- 对每个候选跑上面的 1v1 评估。
- 评分 < 500：权重很小。
- 评分 ≥ 500：对手被锁住时偏好评分最高的（硬克制）；对手没被锁时偏好评分略高于 500 的（软克制，留余地应对对手反换）。
- 按权重随机抽。

**训练 AI 的开盾**（`decideShield`，第 1181 行）：不同于 1v1 模拟的"必开盾"。它先猜对手放的是哪个招（低难度 AI 会给对手能量加随机误差），再综合伤害占比、当前对位好坏、是否最后一只、是否被锁住等算出开和不开的权重，随机抽。

### 8.5 小结：我们要改进的点
- 1v1 模拟里的开盾几乎是"必开"，骗盾因此必定成功。结果对这个假设很敏感，但界面上看不出来。
- 换人和训练模式的开盾都是加权随机，同一局面每次结果不同，无法复现，也无法解释。
- 3v3 没有真正的前瞻：换人只看"当前这只对对面这只"的 1v1 评分，不考虑后续对位、能量和盾的保留。
- 出招搜索还按"大招占 1 回合"算，和 PvPoke 自己更新后的时序（2 回合）不一致。
- 大量规则是针对具体宝可梦或招式的补丁（Registeel、Melmetal 对 Cresselia、Superpower、Obstruct 等），不通用。

### 8.6 简单规则策略与 PvPoke AI 的比较（第 3c 步）
`pogo_sim/simple_policy.py` 是一个刻意简单的基准策略：8 条按顺序判断的出招规则 + 3 种开盾方式，每条都能单独开关或调参，每个决定都写原因进时间线。规则见该文件开头。

用 3b 的 52 场对局（同样的宝可梦、等级、IV、招式、盾数），双方都换成简单规则策略再跑一遍，和 PvPoke AI 的结果比较（`tools/compare_simple_policy.py` 生成 `docs/simple_policy_vs_pvpoke.md`）。引擎已逐回合一致，所以差异全部来自决策。

| 配置 | 胜负与 PvPoke 相同 | 大招序列完全相同 | 评分平均差（满分 1000） |
|---|---|---|---|
| 默认：骗盾 + 出招时机 + 总是开盾 | 49/52 | 16/52 | 38 |
| 不骗盾 | 48/52 | 18/52 | 46 |
| 不优化出招时机 | 51/52 | 13/52 | 25 |
| HP 会低于 50% 才开盾 | 49/52 | 13/52 | 45 |
| 能放就放（最便宜的招） | 47/52 | 5/52 | 72 |

胜负不同的 3 场，原因各是一类决策：
1. **出招时机**（Galvantula vs Azumarill 1-1）：我们要等对手快招"本回合结束"（冷却 1）才放，Galvantula 等了两次，第 21 回合才放 Discharge。PvPoke 对 4 回合以上的长快招放宽到冷却 ≤ 2，第 17 回合就放了。
2. **骗盾**（Mamoswine vs Altaria 1-1）：Avalanche 和 Ancient Power 都是 45 能量。PvPoke 先把弱的 Ancient Power 扔进盾里；我们的骗盾只看"更便宜"的招，于是把 Avalanche 扔进了盾。
3. **选招**（Dewgong vs Swampert 1-1）：PvPoke 选 Icy Wind（必定降对手攻击，被挡也生效）；我们按每点能量伤害选了 Drill Run，完全没考虑能力变化的价值。

其他常见差异（不影响胜负，但影响评分）：
- **开盾例外**：PvPoke 不挡早期的 Power-Up Punch 这类"必定提升自己"的招；自己的主力招会降自己防御时（如 Skarmory 的 Brave Bird）也常不挡（见 8.2）。我们默认总是挡。
- **选招偏好**：PvPoke 有一批按招式的补丁规则（8.3 第 7 步），例如 Altaria 先放 Moonblast 而不是 DPE 更高的 Sky Attack、Obstagoon 先放 Obstruct、Registeel 先放 Zap Cannon。
- **快被打倒时的判断**：PvPoke 推算"还能活几回合"，我们只看对手下一个快招或现成的大招，有时早一回合或晚一回合。

值得注意：关掉我们的"出招时机"规则，胜负和评分反而更接近 PvPoke（51/52、平均差 25）。说明 PvPoke 的时机规则和我们的差别比较大（它有更多例外条件，长快招的窗口也更宽），而"出招时机"对结果的影响不小。

可以考虑的改进（还没做，等用户决定）：
- 骗盾时也考虑"能量相同但伤害更低"的招；
- 选招时给必定生效的能力变化（Icy Wind、Lunge、Power-Up Punch、Obstruct 等）一个价值；
- 出招时机对长快招放宽窗口，或者改成 PvPoke 的条件；
- 开盾加入"不挡必定提升自己的招"之类的例外，做成开关。

### 10.1 格式
- **TOML**：Python 标准库 `tomllib` 能读，不加依赖；能写注释，可以写明数据来源和哪些是假设。
- **字段名与 gamemaster.json 相同**（`speciesName`、`baseStats`、`fastMoves`、`energyGain`……），PvPoke 的条目可以直接复制过来改。合并发生在原始字典这一层，合并后和 gamemaster 走同一套解析。
- 四种表，写法 `[表名.ID]`，按这个顺序应用（先招式后宝可梦，宝可梦可以用同一个文件里新加的招式）：

  | 表 | 作用 | 报错 |
  |---|---|---|
  | `new_moves` | 新招式 | ID 已存在 |
  | `patch_moves` | 修改已有招式，只替换写出来的字段 | ID 不存在 |
  | `new_pokemon` | 新宝可梦 | ID 已存在 |
  | `patch_pokemon` | 修改已有宝可梦，只替换写出来的字段 | ID 不存在 |

  "新"的 ID 撞上已有条目，多半是 PvPoke 后来加了同名条目，要人来决定删掉自定义还是改成 patch；"改"的 ID 不存在，多半是拼错。两种都不悄悄继续。
- patch 是顶层字段整体替换：列表和 `baseStats` 这类嵌套值整个换掉，不做合并。
- 另有 `[meta]` 表放说明（`description`、`sources`），加载时不用。
- 多个文件按给定顺序应用，后面的文件可以修改前面文件新加的条目。

### 10.2 种族值
新宝可梦二选一：
- `baseStats = { atk, def, hp }`：直接给 GO 种族值。
- `mainSeriesStats = { hp, attack, defense, spAttack, spDefense, speed }`：给正作六项，加载时按 2.5 节换算。`tags` 里有 `"mega"` 时用 Mega 的削弱规则（≥ 6000 乘 0.97），否则用非 Mega 的（≥ 4000 乘 0.91）。两条规则可以在 `load_gamemaster` 里换成别的假设。

`patch_pokemon` 也可以写 `mainSeriesStats`，换算结果替换原来的 `baseStats`。

### 10.3 检查
加载时会报错的情况：表名或字段名不认识（字段名以 gamemaster 里出现过的为准）、缺必填字段、属性名不认识、种族值没写全、`speciesId` / `moveId` 和表名里的 ID 不一致、招式数值不是数字；新增或修改过的宝可梦引用了不存在的招式，或快招列表里有大招、大招列表里有快招。

必填字段：
- 新招式：`name`、`type`、`power`、`energy`、`energyGain`、`turns`。快招还是大招按 PvPoke 的规则判断（`energyGain > 0` 是快招，除非写了 `category`）。
- 新宝可梦：`speciesName`、`dex`、`types`、`fastMoves`、`chargedMoves`，以及 `baseStats` / `mainSeriesStats` 之一。`tags`、`extraChargedMoves`、`defaultIVs` 可省略；`released` 不写时为未发布。

## 11. IV 排名

实现在 `pogo_sim/iv_ranking.py`，照 PvPoke `pokemon/Pokemon.js` 的 `generateIVCombinations`（第 469–616 行）。验证状态：**参考 PvPoke**（排名与 PvPoke 逐个核对一致，见 11.4）。

```python
ranking = rank_species_ivs(gm.get_species("froslass_mega"), 1500)
ranking[0].describe()                            # IV 4/15/15，14.5 级，CP 1498，第 1 名（100.00%）
find_rank(ranking, IVs(15, 15, 15)).describe()  # IV 15/15/15，13.5 级，CP 1448，第 3696 名（92.53%）
```

### 11.1 做法
1. 每个 IV 组合（每项从 IV 下限到 15）找 CP 不超过联盟上限的最高等级，范围是"最低等级"到"等级上限"，步长 0.5。在最低等级就已经超过上限的组合不参加排名。没有 CP 上限的联盟（10000）全部在等级上限。
2. 能力值乘积 = HP × 攻击 × 防御，用这个等级的实际值（攻防不取整，HP 取整，见 2.2）。暗影倍率不算进去。
3. 按乘积从大到小排。乘积完全相同时，HP IV、防御 IV、攻击 IV 高的在前（PvPoke 按这个顺序枚举，排序是稳定的）。名次不并列，每个组合一个名次。

乘积最大不等于实战最好：有时更高的攻击能拿到关键的伤害断点。排名只是挑 IV 的一个起点。

等级上限是参数（50、51 最佳伙伴、Mega 的特殊上限等），由调用方按赛季规则给出。

### 11.2 默认的 IV 下限和最低等级（PvPoke 的假设）
`rank_species_ivs` 不传 `iv_floor` / `level_floor` 时用 PvPoke 的默认值，也可以手动指定。

| 条件（后面的覆盖前面的） | IV 下限 | 对应的游戏规则（PvPoke 没写理由，这是推测） |
|---|---|---|
| 其他 | 0 | 野生 |
| 传说或究极异兽，且没有 `wildlegendary` 标签 | 1 | 好友交换 |
| 传说或究极异兽，且是暗影 | 6 | 暗影 Raid |
| 有 `untradeable` 标签（不能交换） | 10 | 调查、Raid |

PvPoke 还有一条：当前招式里有 RETURN（报恩）时下限是 2（净化）。当前 gamemaster 里没有宝可梦能学 RETURN，没有实现。

最低等级：gamemaster 的 `levelFloor`（39 只有，值是 8、15 或 20；例如 Mega 超梦X 是 15），没有的是 1 级。CP 上限 ≤ 500（小小杯）时 PvPoke 忽略它，从 1 级开始（源码注释说"暂时"如此）。

注意：Mega 超梦X 在 15 级时任何 IV 都超过 1500，所以它在超级联盟的排名是空的；但 PvPoke 的 `defaultIVs` 给了它 9 级（第 7 节）。用户确认（2026-11-19）：Mega 在对战中临时降等级时不看最低等级，从 1 级起找（9.1）；赛季规则里按这个处理。

### 11.3 与 PvPoke 写法上的不同（结果相同）
- **等级查找**：PvPoke 从最低等级逐级往上找，CP 正好等于上限时就停；本项目用二分查找"不超过上限的最高等级"。只有相邻两级 CP 相同、又正好等于上限时结果才不同；CP 上限 500 附近相邻两级至少差 2 点，不会出现。
- **HP 最低 10**：本项目的实际 HP 有最低值 10（2.2），PvPoke 排名时不套。扫过全部宝可梦的 500 / 1500 / 2500 排名，只有脱壳忍者（HP 种族值 1）会碰到。它在对战里 HP 固定为 10，两边的排名都没有按这一点处理，对它的排名没有意义。

### 11.4 测试
`tests/test_iv_ranking.py`：
- PvPoke 的 17 个用例（`tools/pvpoke_ref/export_iv_reference.js` 生成）：完整名次顺序、每个组合的等级一致；前 20 名的 CP、实际能力值、乘积浮点逐位相等。用例覆盖：各种 IV 下限、`levelFloor`（含排名为空）、小小杯、最佳伙伴 51 级、`supermega` 在 PvPoke 里的 52 级、大师联盟、种族攻击等于种族防御（乘积并列）。
- Mega 雪妖女（覆盖文件）在超级联盟的排名。
- 二分查找与逐级查找的 2000 个随机对比。

### 12.1 配招和招式池
`pogo_sim/moveset.py`。招式池以 gamemaster（含覆盖文件）为准：快招看 `fastMoves`，第 1、2 个大招看 `chargedMoves`（包括 `eliteMoves` 里的限定招式），第 3 个大招只能从 `extraChargedMoves` 里选（第 7 节）。Mega 专属招式放在第 1、2 个位置算招式池外。

- 覆盖文件里用 `patch_pokemon` 改招式池：适合"假设以后会加这个招"，所有对局都生效；
- 对战配置里给这一套配招写 `outside_movepool = true`：只对这一套生效，报告里在名字后面加 `*`，并在配置说明里写明是哪个招。快招 / 大招的区分和第三个大招的规则照样检查。

## 13. 3v3

### 13.1 PvPoke 的 3v3 是怎么做的
读源码（commit `d02018e`）的结论：

- **PvPoke 没有可复现的 3v3 模拟。** 排名、对战页面、矩阵都是纯 1v1。换人只在训练对战（`Battle.emulate`）里：实时运行（每 500ms 调一次 `step()`，大招和选人的时长用 setTimeout 计时），AI 按权重随机选（8.4），同一局面每次结果不同。所以 3v3 能和 PvPoke 逐回合对照的只有换人在回合里怎么结算（3v3-c）。
- **换人的结算和 1v1 共用 `Battle.step()`**：
  - 换人优先级 +20，先于同回合的大招（+10）和快招（0）；大招后空回合的 0 回合换人再 −40，排在漂浮快招之后（第 422 行，Q3）。
  - 能换的条件：冷却为 0 且换人计时为 0，或者自己已倒下（第 489 行）。换人不加冷却，换上来的下一回合就能行动。
  - 主动换人：开始 45 秒计时；换下去的保留 HP 和能量，能力等级清零（第 987–1014 行）。
  - 倒下后（第 553–610 行）：清空双方排队中的行动，冷却归零；下一回合只处理换人，存活的一方不出招（它的对手 HP 为 0，第 353 行）；换上后对手冷却设为 500ms（第 1007 行），再下一回合双方同时行动。
- **换人计时按真实时间走**（`Player.decrementSwitchTimer` 在 `step()` 开头，暂停阶段也照减）：大招阶段固定 10 秒（instant 招式 3 秒）；倒下后选人最多 13 秒后自动换上第一只；困难 AI 的 `WAIT_CLOCK` 会故意拖 2–7 秒，消耗自己的换人冷却。训练模式没有对战时限。
- **盾**：全队 2 个（`Player.shields`），换上来时同步给场上那只（`setNewPokemon`，第 107 行）。
- **疑似 PvPoke 的问题**（本项目不照搬）：
  - CMP 平手（`usePriority`）只在 `start()` 里按两只首发判断一次（第 262 行），换人后不重算。本项目按当前在场的两只判断（Q20）。
  - 最后一只同时倒下判成"负"：第 595 行先写 `result = "tie"`，紧接着被 win / loss 覆盖。本项目判平局（Q18）。
  - 训练模式的概率效果是真随机，而且换上来时 `resetMoves` 会重置计数器。本项目用计数器，每只各自累计、换下场不清零（Q17）。

### 13.2 本项目的决定（用户 2026-11-19 答复）
机制问题 Q14–Q20 见 9.1。设计：

- **D1 3v3 评分**：把 1v1 的评分直接推广，评分 = 500 + 500 ×（己方剩余 HP 比例之和 − 对方剩余 HP 比例之和）÷ 每队只数，向下取整。赢家一定大于 500，双方加起来 1000，同时倒下是 500；每队一只时就是 PvPoke 的 1v1 评分。另外列出剩余只数和剩余盾。这是本项目的口径，不是游戏规则。
- **D2 对位评估**（换人、选人、开盾都要用）：照 PvPoke 的思路，用本项目的 1v1 引擎和简单规则策略，从当前状态（HP、能量、能力等级）开始打；双方盾数从 0 到当前值的每种组合按 [4, 4, 1] 加权平均。用户提醒 3v3 里可能要更复杂（例如考虑后备），到 3v3-d 再细化。
- **D3 换人策略**：两种都做。(b) 当前对位评分低于阈值、后备里有明显更好的就换——默认；(a) 不主动换人，只在倒下后选对位评分最高的——作为对照的基准。
- **D4 博弈树搜索**：先只做"对固定对手策略的最优应对"（3v3-g）。双方同时决定的完整博弈不做。用户 2026-11-24 又定了三点（13.11）：搜索方法用"逐步试探"（不保证全局最优，但不比原策略差）；我方五种决定（出招、主动换人、0 回合换人、开盾、选人）都可以改；比较时先看胜负，再看评分。
- **D5 环境前 N**：用 PvPoke 的排名文件。有 Mega 的规则下，排名前列大多是 Mega，但每队只能带一只，所以 **Mega 和非 Mega 分开取前 N**。用户 2026-11-21 又定了三点：
  - 排名里取来的宝可梦默认用 IV 排名第 1、等级按赛季规则（和配置文件不写 IV 时一样），另有开关改成 PvPoke 默认 IV；
  - 队伍对队伍（3v3-f2）时，对手队伍是配置里手写的，加上从环境前 N 随机抽的若干队（固定随机种子，可复现；每队最多 1 只 Mega、同一种不重复、出场顺序也随机；报告列出每一队）；
  - 排名文件原样存进 `data/rankings/`（`all` 和 `mega` 两套 × 超级 / 高级 / 大师联盟，共约 5.3 MB），`data/SOURCE.md` 记 commit 和 SHA-256。
- **D6 队伍规则**：3 只（首发 + 2 后备）；同一种宝可梦不能带两只，按图鉴编号判断，所以普通和暗影、普通和 Mega、不同地区形态都算同一种（用户确认，2026-11-19）。6 选 3 不做。
- **时间到**（Q19）：游戏规则是双方都还有宝可梦就平局（默认）。评估时有的对局会很拖，所以另做几种可选的判定标准（3v3-b）。

### 13.4 队伍结构（3v3-a）
`pogo_sim/team.py` 的 `Team`：一方的队伍。
- `members`：按出场顺序，第一只是首发；`active`：在场的是第几只。
- `shields`：**盾属于队伍**，全队共用，不再记在单只宝可梦（`Combatant`）上。
- 1v1 就是每队一只：`Team((azumarill,), shields=2)`。

策略能看到的信息（`policy.BattleView`）改为双方的队伍：`my_team`、`opponent_team`；`me`、`opponent` 是双方在场的那只，写法和以前一样。

这一步只改结构，不加功能。验证：原有的全部测试（含 52 场 PvPoke 逐回合对照）结果不变。

### 13.5 换人结算（3v3-b）
实现在 `pogo_sim/battle.py`，照 PvPoke `Battle.step()` 和训练模式倒下的处理写（13.1）。状态：**参考 PvPoke**，已与 PvPoke 逐回合对照（13.6）。规则的开关见 9.3，每条规则一个场景测试（`tests/test_switch.py`）。

**三种换人**

| 换人 | 什么时候 | 花不花回合 | 换人冷却 |
|---|---|---|---|
| 主动换人 | 可以行动的回合（冷却为 0，也就是快招打完了，Q16），代替出招 | 占用这一回合，换上来的下一回合就能行动 | 要求为 0；换完开始 45 秒 |
| 0 回合换人 | 大招后的空回合，双方都可以（Q15）；对手倒下、正在选人的回合（Q21） | 不花 | 要求为 0；换完开始 45 秒 |
| 倒下后换人 | 在场的倒下后的下一回合 | 不花：换上后双方同时行动 | 不需要，也不开始计时 |

**同一回合里的先后**（优先级高的先结算，同优先级按第 0 方、第 1 方）：
- 换人 20 > 大招 10（CMP 胜方 11）> 快招 0。所以在对方快招完成的回合换人，快招打在换上来的那只身上；在对方大招开始的回合换人，大招也打在换上来的那只身上，开不开盾问的是它（盾是全队的）。伤害按挨打那只的属性和防御算。
- 大招后的空回合，换人优先级 −40，排在漂浮快招之后：漂浮快招打在换下去的那只身上（PvPoke，Q3）。开关改成 `"incoming"` 时换人在前，打在换上来的那只身上。
- 招式的出招方是做决定的那只。挨打的是结算时对方在场的那只。

**换下去的那只**：保留 HP、能量和概率效果计数器（Q17），能力等级清零。

**倒下后**：
1. 倒下的那一回合结束时：清空双方排队中还没结算的行动（时间线里记为 "cleared after a faint"），在场的冷却归零。
2. 下一回合是"换人回合"：倒下的一方先选人（`Policy.choose_replacement`，可以指定选人时等几秒，0 到 13 秒）。选人的等待发生在换人回合之前，等待期间双方的换人冷却照走。然后存活的一方决定换不换：它不出招，只可能 0 回合换人，而且要求（扣掉等待之后的）换人冷却为 0（Q21）。换上来时，对手在场的那只冷却设为 1。
3. 再下一回合双方同时行动。

特例：大招后的空回合要 0 回合换人，但换下去的那只先被漂浮快招打倒了——换人照样进行，按倒下后换人处理（不开始冷却），也不再多一个换人回合。

**换人冷却按对战时间走**：每回合开头扣掉上一回合花的对战时间——普通回合 0.5 秒，有大招的回合按 PvPoke 的计法（约每个大招 10 秒，6.5），倒下后选人的等待也算（在换人回合开头、存活的一方做决定之前扣）。例如第 1 回合主动换人，只打快招的话第 91 回合才能再换（45 秒 = 90 回合）。对战时间（240 秒时限）也含选人的等待。

**胜负**：
- 一方全队倒下，另一方赢；最后一只同时倒下是平局（Q18）。
- 时间到、双方都还有宝可梦：默认平局（游戏规则，Q19）。评估时可以改成"剩余只数多的赢"或"评分高的赢"（`BattleRules.timeout_result`）。
- 注意：这一条对 1v1 也生效。PvPoke 的 1v1 模拟时间到按评分判胜负，本项目默认判平局；评分本身不变，九宫格（只看评分）不受影响。要和 PvPoke 的胜负一致，设成 `"rating"`。
- 评分按 D1（`battle.team_rating`，每队一只时与 PvPoke 逐位相同）。结果里另有双方剩余只数和剩余盾数。

**策略要回答的问题**（`pogo_sim/policy.py`）：`decide_action` 可以返回 `SwitchAction`（`view.can_switch` 时）；`decide_zero_turn_switch` 回答"不花回合的换人机会，换不换"；`choose_replacement` 回答"倒下后换谁、等几秒"。每个决定都写原因进时间线。
- 剧本策略（`ScriptedPolicy`）：`switches` 指定哪一回合换上第几只，`replacements` 指定倒下后换谁；没写时换上队伍里排在最前的。
- 简单规则策略（`SimplePolicy`）：这一版不主动换人，倒下后换上排在最前的。3v3 的换人和开盾策略在 3v3-d。

**时间线**：换人事件（`SwitchEvent`）、决定事件（"switch" / "zero_turn_switch" / "stay" / "replacement"），每个事件记录是第几只出招、打的是第几只；快照里有在场的是第几只、换人冷却、全队每只的 HP 和能量。`timeline.team_names` 取出双方成员的名字给 `format_timeline` 用。

### 13.6 与 PvPoke 对照（3v3-c）
PvPoke 没有可复现的 3v3（13.1），所以对照的是：给定同一个剧本（大招、开盾、换人、倒下后换谁和等几秒），换人在回合里怎么结算。

**做法**（`tools/pvpoke_ref/export_switch_reference.js` 生成 `tests/fixtures/pvpoke_switch_reference.json`，`tests/test_switch_pvpoke.py` 比较）：
- 结算用 PvPoke 自己的 `Battle.step()`（模拟模式 + 沙盒剧本）：换人的优先级、能不能换的检查、换人本身（开始计时、能力等级清零、倒下后换人时对手冷却设 500）都是 PvPoke 的代码。
- 训练模式才有的部分，照抄训练模式的代码写成"胶水"：全队的盾和换人计时用 PvPoke 的 `Player`，换上来时同步全队的盾；在场的倒下时清空排队的行动、冷却归零，下一回合倒下的一方换人（`step()` 末尾 `mode == "emulate"` 的分支）。
- 计时：模拟模式的 `step()` 每回合只扣 0.5 秒。脚本按 Q14 补上大招回合多出的时间和选人的等待（等待放在换人回合之前，和训练模式一样）。计时规则本身是用户定的，不是对照的对象。
- 剧本里的换人由脚本包装 `getTurnAction` 返回（沙盒模式只认大招剧本），优先级的算法与 PvPoke 相同（+20）。
- 每回合比较双方全队每只的 HP 和能量、在场的是第几只、冷却、能力等级、全队的盾、换人计时；还比较每一招的出招方和挨打的是第几只、伤害、开没开盾，每次换人，每次倒下，以及结果（回合数、剩余只数、对战时间）。

**场景**（10 场完全一致，另有 1 场已知差异）：

| 场景 | 检查什么 |
|---|---|
| `active_switch` | 主动换人；换上来的承受同回合完成的快招；换下去的能力等级清零，换回来时 HP、能量不变（换人冷却设成 10 秒以缩短场景） |
| `switch_into_charged_team_shields` | 在对方放大招的回合换人：大招打在换上来的那只身上，开盾用全队的盾；盾用完后剧本要开也开不了 |
| `zero_turn_switch_both_sides` | 大招后的空回合双方都 0 回合换人；漂浮快招先结算，打在换下去的那只身上 |
| `floating_fast_knocks_out_before_zero_turn_switch` | 换下去的那只先被漂浮快招打倒：按倒下后换人处理，不开始计时，没有额外的换人回合 |
| `replacement_wait_and_survivor_switch` | 被快招打倒：清空排队的快招；换上第 3 只并等 4 秒；存活的一方同时换人（Q21） |
| `survivor_switch_timer_runs_out_during_wait` | 存活的一方冷却在对手选人的等待中走完，换人回合可以换 |
| `survivor_in_cooldown_cannot_switch` | 存活的一方还在冷却中，不能换 |
| `charged_knockout_replacement_and_zero_turn_switch` | 被大招打倒（同回合自己的快招作废）；换人回合同时也是大招后的空回合，存活的一方 0 回合换人 |
| `double_knockout` | 双方同时倒下、同时换人，打到一方全队倒下 |
| `full_3v3_simple_policy` | README 里那场完整 3v3（130 回合、14 个大招、4 次倒下后换人），双方的决定抄成剧本 |
| `survivor_switch_side_1` | 已知差异，见下面第 2 条 |

**发现**：
1. **选人的等待放错了位置（已改正）。** 原来的引擎把等待算在换人回合里，下一回合开头才从换人冷却里扣。PvPoke 训练模式是选人期间计时照走，换人回合开始时已经扣过了；游戏里也是先选人、后换上场。差别出现在存活一方的冷却刚好在对手选人期间走完时：PvPoke 在换人回合就能换，原来的引擎不能。现在改成先问倒下的一方换谁、扣掉等待，再让存活的一方决定（`battle.py` 的 `_choose_replacements`）。对战时间的总数不变。
2. **PvPoke 里只有第 0 方能在对手的换人回合换人（已知差异，不照搬）。** 同回合的两个换人优先级相同，按排队顺序先结算第 0 方。倒下的是第 0 方时，它的换人先结算，把对手在场那只的冷却设成 500（`Battle.js` 第 1007 行），接着第 1 方的换人检查"冷却为 0"（第 489 行）不通过。所以在 PvPoke 里，存活的第 1 方既不能做 Q21 的换人，用大招打倒对手后也不能 0 回合换人（Q15）；存活的是第 0 方则都可以。这是结算顺序的副作用，不是规则。用户的规则（Q15、Q21）不分哪一方，本项目照用户的规则。对照场景里存活的一方都放在第 0 方，`survivor_switch_side_1` 把差异本身固定下来（`test_known_difference_survivor_switch_on_side_1`）。
   - 训练模式里每个行动的优先级还要加上玩家编号（第 1 方 +1，第 109 行），同优先级时第 1 方（AI）先结算，情况正好反过来：只有 AI 能换。模拟模式（PvPoke 的 1v1 排名用的）两方都是 0。本项目和模拟模式一样：同优先级先结算第 0 方，不按方加优先级。
3. **模拟模式换上来时不同步全队的盾**（只有训练模式的 `setNewPokemon` 同步，第 107 行）。脚本照训练模式同步。本项目的盾本来就记在队伍上，不受影响。

### 13.7 3v3 策略（3v3-d）
**对位评估**（`pogo_sim/evaluation.py`，D2）：我方某一只对上对手某一只，打下去大概谁占优，0–1000，500 是平手。照 PvPoke 训练 AI 的 `evaluateMatchup` / `runScenario`（`TrainingAI.js` 第 633、815 行）：
- 从双方现在的状态开始打一场 1v1：HP、能量、能力等级、概率效果计数器照现在的值，冷却从 0 开始（PvPoke 用当前冷却，但不带正在进行的快招，两种都不精确，取简单的）。双方都用简单规则策略，配置可换。
- 双方盾数从 0 到现有的盾数，每种组合各打一场，按盾数权重 [4, 4, 1]（0、1、2 盾）相乘后加权平均。
- 每场的评分是 1v1 对战评分。HP 比例按最大 HP 算，所以评估之前已经掉的 HP 也算进去：评分衡量的是"打完时的局面"，不只是这一段的输赢（与 PvPoke 相同）。
- 和 PvPoke 的不同：PvPoke 评估当前对位时平均三种情形（双方骗盾 / 双方不骗 / 不骗，后两种其实一样），评估换人候选时只用"不骗"；本项目只用一种策略配置。都不考虑后备和剩余时间。
- 按双方的完整状态缓存，同一局面不重复模拟。一次评估最多 9 场 1v1，约 7 毫秒。

**3v3 策略**（`pogo_sim/team_policy.py` 的 `TeamPolicy`）。规则由用户确认（2026-11-20），数字都是 `TeamPolicyConfig` 里的参数。

*出招*：照简单规则策略（`TeamPolicyConfig.moves`）。1v1 里没有换人，打出来和简单规则策略完全一样。

*倒下后换谁上*（3v3-d1）：后备里每一只都和对手在场的那只做对位评估（盾数用两队现有的盾），换上评分最高的；评分相同按队伍顺序；不等待。原因里按评分列出每个候选，例如 `best matchup vs Altaria: Registeel 724, Medicham 387`。双方同时倒下时，看不到对手会换谁上，就和对手剩下的每一只评估，取平均。

*主动换人*（3v3-d2，`switching = "threshold"`，D3 的 (b)，默认）。能换的时候（换人冷却为 0、有后备）按顺序判断：
1. 自己 HP 不超过最大 HP 的 25% → 不换（`stay_hp_fraction`；PvPoke 高难度 AI 的做法：快倒的留在场上）。
2. 当前对位评分 ≥ 450 → 不换（`switch_below`；PvPoke 用 500，对手还剩不止一只时高难度 AI 用 450）。
3. 后备里评分最高的那只 ≥ 500（`switch_target_min`）、而且比当前高 100 以上（`switch_margin`）→ 换上它；否则不换。

- 主动换人占用这一回合。不花回合的换人机会（大招后的空回合、对手选人的回合）用同样的规则；对手在选人时，"对手"按它剩下的每一只取平均。
- 只看一步：不考虑对手换人后的反换、不"攒完能量再换"、不偏好"软克制"（PvPoke 在对手还能反换时偏好评分略高于 500 的候选），换上评分最高的。
- 对位评估只在局面明显变化时重算（`reevaluate = "on_change"`，PvPoke 训练 AI 的做法）：任一方换了人（含倒下后换人）、任一方放了大招（在场那只的能量比上次看到的少，或盾数变了）、自己的换人冷却刚走完。其余回合沿用上次的结论，快招造成的 HP、能量变化不触发重算。`"every_decision"` 每次都重算，慢约 3 倍。
- 原因：重新评估的那一回合，结论写在原因最前面，例如 `switch: matchup vs Swampert 297 < 450, Medicham 539 >= 500 (Medicham 539)`、`stay: matchup vs Trevenant 360 < 450, no bench option >= 500 (Registeel 335, Medicham 170); ...`。沿用结论的回合只写出招的原因。
- `switching = "never"`：不主动换人（D3 的基准 (a)）。

*开盾*（3v3-d3）：先照简单规则策略决定；它说要开时，再看"不在必输的对位上开盾"（`save_shields_for_bench`）：
- 后备还有、而且开了盾这一只仍然输（开盾后的局面——HP 少 1、少一个盾——对位评分 < 500，`save_shield_below`）→ 不开，把盾留给后面。原因例如 `save shield for the bench: even with a shield, matchup vs Swampert 464 < 500`。
- 开了盾也活不下来（HP 只剩 1）→ 不开。
- 没有后备了 → 照简单规则策略（盾没有别的用处）。
- 简化：开盾后的评估不计来招的能力变化效果。

*骗盾*：照简单规则策略（对手有盾就先放便宜的招），3v3 不另加规则。

**例子**：README 里那两队双方都用默认的 `TeamPolicy`，B 赢，评分 387 vs 612，126 回合。换人 7 次：3 次大招后的 0 回合换人、1 次主动换人、3 次倒下后换人；有 3 次"留盾给后面"。两种重算方式这一场结果完全一样（一般不保证）。只保留"倒下后换上评分最高的"（`switching = "never"`、`save_shields_for_bench = False`）时：第 56 回合 A 换上对 Altaria 评分 724 的 Registeel，而不是排在前面、评分 387 的 Medicham；B 赢，评分 374 vs 625，123 回合。

### 13.8 3v3 配置文件与报告（3v3-e）
`pogo_sim/team_battle.py`，格式写在模块开头，例子 `experiments/gl_3v3_example.toml`，用 `tools/run_team_battle.py` 运行，报告写进 `docs/experiments/`。

**配置**（TOML）：
- 和 1v1 配置相同的部分：覆盖文件、联盟、赛季规则预设；一只宝可梦的写法同 `[[subject]]`（种类、配招，可选 label、IV、等级、挚友、Mega 等级、`outside_movepool`），不写 IV 和等级时按赛季规则取 IV 排名第 1 和合法的最高等级。
- `[[team]]` 正好两队，第一队是第 0 方；每队有 `name`（两队不能同名）、可选 `shields`（默认 2），`[[team.member]]` 按出场顺序写，第一只是首发。
- `[policy]`：双方的 `TeamPolicyConfig`，子表 `[policy.moves]`、`[policy.evaluation]` 是两个 `SimplePolicyConfig`。`[team.policy]` 只改这一队，逐项覆盖 `[policy]`（子表也逐项合并）。不写就是默认的 `TeamPolicy`。
- `[rules]`：`BattleRules` 的字段（例如 `timeout_result`、`switch_cooldown_ms`），不写就与 PvPoke 一致。`mega_move_bonus` 这种元组不能在配置里改。
- 写错的字段、类型、取值都会报错，信息里指出是第几队、第几只。

**队伍检查**（建配置时；`season.check_team` 和 `team_battle.py`）：
- 每队正好 `BattleRules.max_team_size` 只（默认 3，D6）。
- 同一种宝可梦不能带两只：按图鉴编号判断，普通和暗影、普通和 Mega、不同地区形态都算同一种（D6，用户确认 2026-11-19）。
- Mega 不超过赛季规则的 `max_megas_per_team`（默认 1）。
- 同一队里名字（label）不能重复。两队都有的名字（镜像）在时间线和报告里后面加队名，例如 `Azumarill (Team A)`。

**报告**（Markdown），按顺序：
1. 设置：配置文件、联盟和赛季规则、和 PvPoke 默认不同的机制规则、覆盖文件、策略和评分口径。
2. 两队：每只一行（CP、等级、IV、配招），策略参数（和默认不同的）；队伍检查通过。
3. 结果：谁赢、评分、剩余只数和盾、回合数、对战时间。
4. 每只的情况：剩余 HP 和能量、造成和受到的伤害（被盾挡下算 1，倒下时的溢出伤害也算）、快招次数、放了哪些大招、挨大招时开盾 / 有盾没开的次数、哪一回合倒下。
5. 开局对位评分：一队每一只对另一队每一只的对位评估（13.7，满 HP、0 能量、两队开局的盾数），就是 TeamPolicy 选人、换人看的评分。两队评估配置相同时只列第 0 方的（第 1 方约等于 1000 减它）。
6. 对位分段：在场的两只不变的一段算一段，一段一行（4b 加的，14.4）。
7. 换人：每次换人的回合、类型和策略给的原因。
8. 大招和开盾：每个大招的结果和开不开盾的原因。
9. 带原因的完整时间线（`--no-timeline` 不附）。

对战是确定的（概率效果用计数器），同一个配置每次结果相同。配置文件只是换个写法：和直接用同样的配置、`TeamPolicy` 打一场完全相同（测试里核对）。

**例子**：README 里那两队，但不写 IV，用 IV 排名第 1（和 README 用的 PvPoke 默认 IV 不同）。B 赢，评分 221 vs 778，100 回合：第 31 回合 B 在 Swampert 的大招后 0 回合换上 Trevenant（对 Azumarill 评分 644），Trevenant 一只打倒了 A 的三只。结果在 `docs/experiments/gl_3v3_example.md`。

**顺带的改动**：
- 1v1 配置（`matchups.py`）的共用部分移到 `config.py`，行为和报错信息不变（`docs/experiments/mega_zygarde_ml.md` 重新生成后逐字相同）。
- 时间线里名字一栏补齐到 16 个字符，更长的名字以前会和后面的字连在一起（例如 `Thundurus (Incarnate) (Shadow)`，也影响 1v1），现在后面至少空两格。16 个字符以内的输出不变。
- `report.format_setup` 支持多于一只的队伍。

**测试**：`tests/test_team_battle.py`（示例配置的结果、和直接打一场相同、策略和规则参数、每队的盾、镜像的名字、每只的统计加起来对得上、开局对位评分、报告内容、留盾在报告里的样子、写错的配置 20 多种、队伍检查），`tests/test_season.py`（同一种：暗影、Mega、地区形态），`tests/test_team.py`（队伍的配置文字）。

### 13.9 环境前 N（3v3-f1）
**排名快照**：`data/rankings/<cup>/overall/rankings-<CP 上限>.json`，PvPoke commit `d02018e`（和 gamemaster 相同），原样保存，SHA-256 和条目数记在 `data/SOURCE.md`（`tests/test_rankings.py` 核对）。两套排名：
- `all`：普通的超级 / 高级 / 大师联盟，不含 Mega；
- `mega`：Mega 版联盟，Mega 和非 Mega 一起排（超级联盟里第 1 名是 Mega 勾魂眼，第 2 名起是非 Mega，第二只 Mega 是第 32 名）。

**取环境前 N**（`pogo_sim/rankings.py`）：
- 按 D5，Mega 和非 Mega 分开取：`kind = "mega"` / `"non_mega"`，在这一类里按名次数前 N 只。报告里写排名文件里的名次（两类一起排），所以非 Mega 前 50 的名次是 2、3、4……52（跳过第 32 名的 Mega 乌贼王）。

- 建配置主要花在 IV 排名上，一只约 20 毫秒，前 50 只约 1 秒。

1. 来源说明，和建不了配置、跳过的几只；
2. 对手表：名次、宝可梦、PvPoke 的综合分、CP、等级、IV、配招；
3. 总表：每个测试对象在双方 0 盾、1 盾、2 盾时各赢了几只，九种盾数一共赢了几格，全部评分的平均；
4. 每个测试对象一张表：一行是对一个对手的九宫格（列是"自己的盾数 对 对手的盾数"），赢的（评分大于 500）加粗，最后是九格里赢了几格和平均评分。

### 13.10 队伍对队伍（3v3-f2）
`pogo_sim/team_matrix.py`，格式写在模块开头，例子 `experiments/gl_team_matrix_example.toml`，用 `tools/run_team_matrix.py` 运行，报告写进 `docs/experiments/`。

**配置**（TOML）：
- 和 3v3 配置（13.8）相同的部分：覆盖文件、联盟、赛季规则、`[rules]`、`[policy]`（所有队伍共用，各队再逐项覆盖）。
- `[[team]]`：我方队伍，一队或几队，写法同 3v3 配置的 `[[team]]`（`name`、可选 `shields`、`[team.policy]`、`[[team.member]]`）。
- `[[opponent_team]]`：手写的对手队伍，写法相同。
- `[opponent_sample]`：从环境前 N 随机抽对手队伍。`rankings`（哪套排名）、`top`（非 Mega 候选：这一类的前 top 只）、`count`、`seed` 必写；可选 `mega_top`（默认 0）、`ivs`（同 13.9）、`shields`、`[opponent_sample.policy]`。
- 手写和抽样至少写一种。所有队伍的名字都不能重复；抽样的队伍叫"抽样 1"……"抽样 N"。

**抽样**（D5，用户 2026-11-21）：
- 候选就是 13.9 的环境前 N：Mega 和非 Mega 分开取，建不了配置的跳过，报告里写明。
- 每一队：`mega_top` 大于 0 时，先从 Mega 候选里均匀抽 1 只，所以每队正好 1 只 Mega；`mega_top = 0` 时不带 Mega。再把非 Mega 候选洗牌，按顺序取，跳过和已选的同一种的（按图鉴编号，D6），取满一队。最后把这一队的出场顺序洗牌，Mega 可能是首发，也可能是后备。
- 均匀抽，不按名次加权。成员相同（不论顺序）的队伍只留一个，重抽；试了 `count` × 50 次还抽不够时报错（候选太少）。
- 可复现：随机数只用 `random.Random(seed).random()`，Python 只保证它在不同版本下对同一个种子给出同样的序列（`randrange`、`shuffle` 不保证）。抽样一队一队进行，`count` 调大时前面的队伍不变。
- 抽到的队伍也过一遍队伍检查（13.8）。

**对战**：我方每一队对每一队对手打一场 3v3，我方是第 0 方，双方都用 `TeamPolicy`。每队只建一次配置。对位评估器按评估配置在全部对战之间共用（`MatchupEvaluator` 的缓存键是双方的状态、盾数和规则，不含是哪一场），只是快，结果和每一场单独打相同（测试里核对）。对战是确定的：同一个配置每次结果相同。

**报告**（Markdown），按顺序：
1. 设置：配置文件、联盟和赛季规则、和 PvPoke 默认不同的机制规则、覆盖文件、对战的组织方式、策略和评分口径。
2. 我方队伍：每只一行（CP、等级、IV、配招），策略参数（和默认不同的）。
3. 总表：我方每一队对手写的、抽样的、全部对手，各几场、赢平输、我方的平均评分、平均剩余只数。
4. 我方每一队一张表，一场一行：对手队伍、对手成员（按出场顺序，抽样的带排名名次）、结果（时间到另注）、评分、剩余只数、剩余盾、回合数。赢的加粗。
5. 对手队伍：手写的配置；抽样的说明、跳过的候选、每一队的成员、候选表（名次、PvPoke 综合分、CP、等级、IV、配招）。

`--csv` 另外把全部对战写成一场一行（`team, opponent_group, opponent, opponent_members, result, timed_out, team_rating, opponent_rating, team_remaining, opponent_remaining, team_shields_left, opponent_shields_left, turns`）。`--battle 我方队伍 对手队伍` 只打这一场，输出 13.8 的完整 3v3 报告（换人和开盾的原因、时间线）。

### 13.11 对固定对手策略的应对（3v3-g）
`pogo_sim/best_response.py`。用 `tools/run_team_battle.py` 加 `--best-response 队名`，或者 `tools/run_team_matrix.py --battle 我方 对手 --best-response`（搜索我方）。

**用户的选择**（2026-11-24）：搜索方法用"逐步试探"；我方五种决定都可以改；比较时先看胜负，再看评分。

**为什么不穷举**：实测一场里我方有 40–50 个出招决定（其中 15–45 个能换人、6–15 个能放大招），另有 2–4 次开盾、3–7 次 0 回合换人、2 次倒下后选人，全部组合跑不完。

**方法**（逐步试探，rollout）：
1. 起点：双方都照各自的 `TeamPolicy` 打一场（"原策略"）。
2. 沿着当前最好的一场，按顺序看我方的每一个决定点。有不止一个选项时，把其余每个选项都试一遍：这个决定点之前的决定照当前最好的一场，这一个换成这个选项，之后双方照各自的策略打完。
3. 打出来严格更好，就换成它（几个选项都更好时取最好的；一样好时取排在前面的）。然后看下一个决定点，直到最后一个。改了以后，后面的决定点会变，所以每次都看当前最好的那一场。

性质：
- 每一步只在严格更好时才改，所以结果不比原策略差（测试里核对每次改动都是严格更好、一环接一环）。
- 不保证全局最优：一次只改一个决定，而且试探时假定之后的决定照原策略。
- 对手的策略是确定的，搜索完全知道它会怎么应对（完全信息）。结果是"对这个对手策略"的打法，可能利用了 `TeamPolicy` 规则里的弱点，不一定适用于真人对手。

**我方可以改的决定**：
- 出招：快招、能量够的每个大招（所以攒能量、骗盾、提前放的时机都在搜索范围里）、能换人时换上每一只后备；
- 开盾：开 / 不开；
- 不花回合的换人：不换 / 换上每一只后备；
- 倒下后换谁上：每一只后备。选人的等待不搜，照原策略（`TeamPolicy` 是 0）。

**比较两场**：先比胜负（从我方看，赢 > 平 > 输），再比我方评分（D1）；一样时保留原来的选择，让改动尽量少。所以险胜好过评分更高的平局。

**实现**：
- `SteeredPolicy` 包着我方的原策略：每个决定都先问原策略，再按指定（第几个决定 → 选项）换掉，并记下每个决定点（回合、种类、选项、原策略的选择、实际的选择）。原策略每次都被问到，所以它内部的状态（换人判断的缓存）在每次重打时都一样。
- 每次试探都从第 1 回合重打：对战是确定的，前面的决定照抄就能复现同样的局面。规则里有用随机数的开关时，每次试探用同一个种子。
- 对位评估器在全部试探之间共用（缓存键不含是哪一场），只是快。示例一场搜索约 0.4–2 秒（几十到一百多场重打）。

**报告**（Markdown）：
1. 设置和两队。搜索的一方，策略那一行写明打法是搜索出来的，以及原策略是什么。
2. 搜索结果：原策略和搜索后的结果；我方一共几个决定、几个有不止一个选项（都试过）、改了几个；一共打了几场、用时。
3. 改了哪些决定：按搜索的顺序，每行是回合、决定的种类、原策略的选择、改成什么、改之前和改之后的结果（胜负和评分），以及这个决定点每个选项打出来的结果。
4. 试过的全部决定点（4e 加的）：每个有不止一个选项的决定点一行，按搜索的顺序，写原策略的选择、搜索后的选择（改了的加粗，没改的写"同原策略"）和每个选项打出来的结果。例子里 32 行。
5. 搜索后的这一场：每只的情况、开局对位评分、换人、大招和开盾、时间线（同 13.8）。改过的决定，原因写成 `best response: …（policy would …: 原策略的原因）`。

**例子**：`docs/experiments/gl_3v3_best_response.md`，3v3 例子（`experiments/gl_3v3_example.toml`）里 Team A 对 Team B 的 `TeamPolicy`。原策略输，评分 221；搜索后赢，评分 593。改了 5 个决定，一共打了 50 场：

| 回合 | 原策略 | 改成 | 改之前 → 改之后 |
|---|---|---|---|
| 1 | 快招 BUBBLE | 换上 Medicham（对首发的 Swampert） | 输 221 → 输 465 |
| 11 | 开盾 | 不开盾 | 输 465 → 赢 521 |
| 21 | 快招（攒能量放 PSYCHIC） | 先放 ICE_PUNCH | 赢 521 → 赢 577 |
| 62 | 不换 | 0 回合换上 Registeel | 赢 577 → 赢 588 |
| 99 | 不换 | 0 回合换上 Azumarill | 赢 588 → 赢 593 |

另外：Team B 一方本来就赢，搜索后评分从 778 到 785（第 23 回合提前放 HYDRO_CANNON）；队伍对队伍例子里 Team A 对"抽样 3"，从输 449 到赢 626（`--battle "Team A" "抽样 3" --best-response`）。

**顺带的改动**（`team_battle.py`，3v3 和队伍对队伍的报告逐字不变）：报告拆成 `format_settings`、`format_teams`、`format_battle_details` 几部分，策略那一行的文字是 `policy_text`（队伍对队伍也用它）。

**测试**：`tests/test_best_response.py`（什么都不指定时和正常打一场完全相同、各种决定点的选项、指定的决定照做并写明原因、指定的选项现在不能选时报错、比较方法、示例的搜索结果、每次改动严格更好而且一环接一环、按搜索结果重打得到同样的一场、另一方的搜索、报告的各节、示例报告是最新的）。

**以后可以做的**（没做）：多轮搜索（拿搜索出来的打法当新的起点再搜一遍）；小范围内的穷举，用来检查逐步试探离最优有多远；队伍对队伍的每一场都搜（102 场估计 1–2 分钟）；选人的等待也搜。

## 14. 网页界面

路线图第 4 步。原则（CLAUDE.md）：网页只是交互界面，核心逻辑全在 Python 引擎里。浏览器只负责填表和显示，建配置、检查、对战、统计都由本地服务器调引擎。

### 14.1 已定的需求（用户 2026-11-24）
**整体**：
- 技术栈：服务器用 Python 标准库的 `http.server`，不加依赖；前端用原生 HTML / JS / CSS，不用 npm、不用构建。只监听本机 127.0.0.1，只适合本机一个人用。
- 名字：界面文字用中文；宝可梦和招式用 gamemaster 里的英文名，搜索也认 ID。中文名以后加翻译表（要另找数据源）。
- 测试：Python 部分用 pytest（接口函数直接测，另起一个服务器用标准库 urllib 测）；JS 不加测试框架，只做表单和显示，在浏览器里手动核对。
- 队伍库（`teams/` 一队一个文件）：4a 不做，浏览器记住上次填的；以后再定是导入导出 TOML 还是队伍库。
- 图形：不用官方的宝可梦图片（版权属于任天堂 / 宝可梦公司；PvPoke 的 MIT 许可证只覆盖它的代码和数据），也不照着 GO 的对战画面做，自己画简单的图形。

**战斗过程图（4b）**：用户提的布局——上面是双方的招式带，下面是双方的 HP 带，共用一根时间轴。另外：
- 快招画成小块，宽度 = 招式的回合数；大招画成标记，写招名和伤害，被挡下的加盾形符号；换人画竖线并写换上谁，倒下画 ✕。
- HP：每只一种颜色，后备画淡色；能量画成细虚线。横轴是回合和对战时间，大招期间的暂停不占宽度。
- 鼠标移到某一回合上显示详情（伤害、能量、原因），点一下跳到时间线表的那一行。
- 图下面一张"对位分段表"：每段是一组在场的对位（从哪回合到哪回合、谁对谁、双方快招次数、大招、开盾、HP 变化、怎么结束的）。
- 手画 SVG，不加图表库；分段的逻辑写在 Python 里（以后 Markdown 报告也能用）。

**手动对战（4c）**：自己操作一队，和 `TeamPolicy` 打。
- 先做回合制：每个决定点停下，等玩家选；开盾不限时。实时以后再定。
- 选项：快招（默认）、大招、换人、什么都不做。"什么都不做"要在引擎里加一个"等待"动作（不出招，能量不变，下一回合再决定；PvPoke 训练模式里不点就是这样）。
- 大招没有蓄力小游戏，威力可以自己选：拖动条，默认 100%，旁边实时显示伤害和对面剩下的 HP，并标出"打死至少要 X%"和"不打死最多 Y%"（实战里常故意不放满，留一点血再用快招攒能量）。每个百分比的伤害由 Python 算好发给浏览器。
  - 范围：gamemaster 里没有每只宝可梦 / 每个招式各自的范围。PvPoke 训练模式的倍率 = min(0.25 + 0.75 × 蓄力进度, 1)（`training/BattleInterface.js` 第 213 行），也就是 25%–100% 连续，所有招式一样。最低 25% 做成规则参数。状态：**参考 PvPoke**（用户实战也觉得有最小值）。
  - AI 开盾时按 100% 的伤害判断：PvPoke 的 AI 也是这样（`TrainingAI.decideShield` 用满蓄力算伤害），游戏里防守方开盾时也看不到对方蓄了多少。
- 开盾提示只说"对方放大招了"，不说是哪一招。
- 测试环境默认全部显示：对方的队伍、HP、配招，实时显示对方的能量、每个大招够不够、还差几次快招（例如对方大招要 60 能量、现在 50，能直接看到）。
- 实现：引擎不改结构，沿用 3v3-g `SteeredPolicy` 的做法——浏览器记着我方到现在做的每个决定，每次把这串决定发给服务器；服务器从第 1 回合重打，打到下一个要我方决定的地方停下，返回当前局面、对方刚才做了什么、我方现在能选什么。重打一场不到 0.05 秒；服务器不存状态；打完的一场和自动对战一样有时间线和过程图，也能交给 best-response。

**能力值排序（4d）**：PvPoke 没有的坦度排序和可以自己定的排序。
- 坦度 = 实际防御 × 实际 HP，按联盟的 CP 上限算：等级按赛季规则，IV 用 IV 排名第 1（和项目里其他地方一致），暗影的防御倍率算进去。
- 列：CP、等级、IV、攻、防、HP、坦度、能力值乘积、种族值，每一列都能排序；另有一列"攻^a × 防^b × HP^c"，a、b、c 自己填（0、1、1 就是坦度）。
- 筛选（用 gamemaster 的标签）：排除 Mega、传说、幻之、究极异兽、暗影；只看已实装；属性；只看 PvPoke 排名前 N。覆盖文件里的自定义宝可梦也一起排。
- IV 排名一只约 22 毫秒，全部 1621 只约 35 秒：每个联盟第一次打开时算一遍，存进本地缓存（`.cache/`，不入库）。
  （实际做的时候改成多进程并行算，见 14.6。）

**剩下的四项（用户 2026-11-25）**：best-response、1v1 九宫格和环境前 N、队伍对队伍、保存队伍。按这个顺序一项一项做（4e–4h）。

### 14.3 本地服务器和打一场 3v3（4a）
运行：`.venv/bin/python -m tools.run_web`，自动打开 http://127.0.0.1:8000（`--port` 换端口，`--no-browser` 不开浏览器）。

**文件**：
- `pogo_sim/web_api.py`：接口，收 dict、回 dict（都能直接转成 JSON），只做转换。
- `tools/run_web.py`：服务器，把接口转发成 HTTP，并提供 `web/` 下的文件（只认这一层的 .html / .js / .css）。
- `web/`：`index.html`、`app.js`、`style.css`；几页共用的 `common.js`（4d）、`editor.js`、`battle_view.js` 和 `library.js`（4g，见 14.9）。另外三页是 `stats.html` + `stats.js`（4d）、`matchups.html` + `matchups.js`（4g）和 `matrix.html` + `matrix.js`（4h）。

**接口**（都回 JSON；配置写错回 400 和 `{"error": 中文说明}`，信息和配置文件写错时一样，开头是"网页"；意外错误回 500，详细信息打印在终端）：

| 接口 | 做什么 |
|---|---|
| `GET /api/options` | 联盟、赛季规则、覆盖文件（`[meta]` 的说明）、策略的可选值、例子配置（`experiments/gl_3v3_example.toml`） |
| `GET /api/species?league=1500&custom=a.toml` | 全部宝可梦（名字、属性、标签、是否实装、是否覆盖文件新加的、招式池、第三个大招能选的、搜索用的文字）和招式；PvPoke 在这个联盟的推荐配招（排名文件里有的话；先看普通排名，Mega 看 Mega 版排名）和名次（普通排名；Mega 另给 Mega 版排名的名次） |
| `POST /api/build` | 一只宝可梦按赛季规则建配置：CP、等级、IV、实际能力值、建配置的说明 |
| `POST /api/team-battle` | 打一场 3v3（双方 `TeamPolicy`）：结果、两队的配置、每只的情况、开局对位评分、换人和大招（带原因）、逐回合时间线、Markdown 报告 |

**配置**：网页发来的配置和 3v3 配置文件（13.8）写法一样、键也一样，走同一套检查（`team_battle.parse_team_battle_config`）。只有覆盖文件不同：只能从 `data/custom/` 里选，写文件名，不能写任意路径。网页不编辑说明文字，所以报告开头没有那一段，其余和命令行的报告逐字相同。

**页面**：
- 设置：联盟、赛季规则、勾选覆盖文件。
- 两队：队名、盾数、主动换不换人（`switching`）。每只：从可以搜的下拉框里选宝可梦（选了以后先填 PvPoke 推荐的配招，没有就取招式池前几个）。点一下就列出全部（按 PvPoke 这个联盟的排名，排名外的和 Mega 按图鉴编号排在后面）；输入英文名的一部分可以缩小范围，几个词不分先后，每个词都要在 `web_api.search_text` 给的文字里出现（名字、名字去掉空格、ID、legendary / mythical / ultrabeast 标签、Mega 含原始回归、少数别名如 Zygarde Complete Forme 的 "100%"），例如 `mega venu`、`zygarde 100`；去掉重音和标点（`flabebe`、`mr mime`、`mrmime`）。旁边的"形态"下拉框列出同一图鉴编号的各形态（普通、暗影、Mega、地区形态……），可以直接换；快招、大招从招式池里选（Mega 有第三个大招时多一格）；"更多设置"里有名字、IV、等级、挚友、Mega 等级、允许招式池外的招，以及建配置的说明。每只改完由服务器算出 CP、等级、IV 显示在下面，写错的当场显示原因。
- 打一场之后：结果一行；每只的情况；开局对位评分（大于 500 绿、小于 500 红）；换人和大招的表（带原因）；逐回合时间线（每回合一行，双方各一列，最后一列是回合结束时双方在场那只的 HP、能量和盾；可以关掉"决定和原因"）；下载 Markdown 报告。改了配置以后结果上方提示"还是上一次的结果"。

### 14.4 战斗过程图和对位分段（4b）
需求见 14.1。数据都由 Python 从一场的事件和逐回合快照算出来（不重新打），网页只负责画。

**对位分段**（`pogo_sim/battle_summary.py` 的 `battle_segments`）：在场的两只不变的一段时间算一段，任一方换人（主动、0 回合、倒下后）就开始新的一段。
- 按事件发生的顺序切：换人之前结算的招式算前一段。大招后的空回合里，先结算的漂浮快招打的是换下去的那只，算前一段，所以前一段的最后一回合可能就是后一段的第一回合。
- 同一回合、还没有招式结算时的几次换人只算一次切换（双方同时倒下后各自换上；双方在大招后的空回合都 0 回合换人；第 1 回合就主动换人时不单独算一段 0 回合长的首发对位）。
- 倒下算在那一只在场的那一段：换下去的那只先被漂浮快招打倒时（13.5 的特例），倒下的事件记在换人之后，但仍算前一段。
- 每一段记双方在场那只：开始之前和最后一回合结束时的 HP、能量，快招结算了几次，放的大招（伤害，是否被挡下），造成的伤害，开盾挡下对方大招的次数；以及怎么结束的（谁倒下了、哪一方主动 / 0 回合换人；最后一段没有倒下时写"时间到"）。
- 报告（13.8）在"开局对位评分"后面加了"对位分段"一节，一段一行；网页同样一段一行。

**招式带**（`lane_items`）：每方一条。快招从决定的回合画到结算的回合；大招、换人、倒下是某一回合上的标记；排了队但作废的招式（例如被大招打倒的那一回合的快招）画成虚线框。

**快照里的对战时间**：`TurnSnapshot` 加了 `elapsed_ms`（这一回合结束时的对战时间，同 `BattleResult.elapsed_ms` 的口径：大招按 PvPoke 的计法另加时间，含倒下后选人的等待），图的横轴和悬停详情用它标"几分几秒"。只是多记一个数，对战过程不变。

**图**（`web/app.js`，手画 SVG）：
- 从上到下：A 的招式带、B 的招式带、A 的 HP、B 的 HP，共用横轴。横轴每格是一个回合，每 10 回合（超过 200 回合时每 20 回合）标回合数和对战时间；大招期间的暂停不占宽度。
- 招式带：快招是小块（宽度是回合数），大招是竖条（空心是被挡下），旁边写招名和伤害（标签放两行，避免重叠），紫色虚线是换人（写换上谁），✕ 是倒下。每只一种颜色（A 蓝 / 青 / 紫，B 橙 / 黄 / 粉）。
- HP：每只一条阶梯线，在场时是粗线、后备时是细的淡线；在场那只的能量是同色虚线（0–100）。
- 鼠标移到某一回合上：显示这一回合的对战时间、全部事件（含决定和原因）、回合结束时双方的状态；点一下跳到时间线表的那一行（那一回合没有事件就跳到前面最近的一行）。鼠标移到分段表的一行上，图上标出这一段。
- 回合多时图比页面宽，可以左右滚动（每回合至少 5 像素）；窗口宽度变了会重画。

**接口**：`POST /api/team-battle` 另外返回 `segments`（分段，加上报告用的文字 `charged_text`、`end_text`）和 `chart`（`elapsed_ms`、每方的 `active`、`hp`、`energy`、`max_hp`、`lane`，都是从第 0 回合开始、下标就是回合数的数组；`move_names`）；时间线每回合另有 `elapsed_ms`。

**测试**：`tests/test_battle_summary.py`（例子那一场的分段、怎么结束的文字、时间到、第 1 回合换人不单独成段、报告里的一节；几场不同的对战——不主动换人、换首发、时间到、带 Mega 雪妖女——分段首尾相接、各段的快招 / 大招 / 伤害 / 开盾加起来等于整场、同一只连着两段时 HP 接得上、倒下对得上；招式带和事件一一对应、快招从决定的回合开始；快照里的对战时间；用 3v3-c 和 PvPoke 对照过的换人场景检查边界情况：双方同时 0 回合换人和漂浮快招、漂浮快招打倒换下去的那只、同时倒下、对手选人时存活的一方换人、开局 HP 不满），`tests/test_web_api.py`（分段和图的数据与引擎一致）。图本身在浏览器里手动核对过（悬停、点击跳转、分段高亮、标签不重叠、不超出右边）。示例报告 `docs/experiments/gl_3v3_example.md`、`gl_3v3_best_response.md` 重新生成，只多了"对位分段"一节。

### 14.5 手动对战（4c）
需求见 14.1。4c 拆成两步：4c-1 是引擎和接口，4c-2 是页面（这一节最后）。

**引擎：等待**（`policy.WaitAction`）：这一回合什么都不做——不出招，能量不变，冷却保持 0，下一回合再问。对手照常出招，自己照样可以开盾，换人冷却照走。时间线里是 `decides to wait`。PvPoke 训练模式里没有排行动的回合也是什么都不发生。策略（`SimplePolicy`、`TeamPolicy`）不会选它；best-response 的搜索也不试它（搜索的选项不变，3v3-g 的结果不变）。

**引擎：大招威力**（`ChargedAction.charge`，`BattleRules.min_charge`）：
- 伤害按威力算（`damage.calculate_damage` 的 `charge`，乘在 PvPoke 同样的位置），能量照扣，能力变化照常。范围 `min_charge`（默认 25%，参考 PvPoke 训练模式，用户实战也觉得有最小值）到 100%，超出时引擎报错。
- 守方开盾时看到的伤害按满蓄力算（`decide_shield` 的 `damage`）：开盾时看不到攻方蓄了多少（用户 2026-11-24；PvPoke 的 AI 也按满蓄力判断）。
- 时间线里没放满的大招写威力，例如 `CHARGED PLAY_ROUGH at 60% -> 30 dmg`；对位分段里写"PLAY_ROUGH 30（威力 60%）"；`MoveEvent.charge`、招式带的 `charge` 记下威力。
- 模拟里所有策略都是 100%，所以原有的结果都不变（全部测试照旧通过）。

**重打到下一个决定点**（`pogo_sim/manual.py`）：
- 玩家到现在做过的每个决定按顺序存成列表（`ManualDecision`）。玩家这一方用 `ManualPolicy`：引擎每问一个决定就按列表依次回答；问到列表之后的决定时抛出 `DecisionNeeded`，`play_manual` 接住，返回停下来的引擎（当前的队伍状态、到现在为止的事件和快照）和问题（`ManualQuestion`：第几个决定、第几回合、问什么、能选什么）。另一方用配置里的 `TeamPolicy`。
- 四种问题，同 `Policy` 的四个方法：出招（快招、什么都不做、能量够的大招、能换时换上每一只后备）、开不开盾、不花回合的换人（不换 / 换上每一只后备）、倒下后换谁（不等待）。
- 每次都从第 1 回合重打：对战是确定的，前面的决定照抄就能复现同样的局面。一个例子全程 66 个决定，每次重打最多约 0.02 秒。服务器不用记状态，撤销上一步就是去掉最后一个决定。
- 决定和问的问题对不上（种类不同、现在不能选、威力超出范围），或者对战打完了还多出决定，都报错，写明是第几个决定、第几回合。
- 打完以后的报告（`format_manual_report`）和 3v3 报告一样，只是写明哪一方是玩家操作的；玩家的决定在时间线里的原因是 `player`。

**接口** `POST /api/manual-battle`：请求是 `{"config": 和打一场一样的配置, "side": 玩家操作哪一方, "decisions": [到现在的决定]}`。同一套配置只建一次两队（缓存最近 8 套，键里含覆盖文件的修改时间）：第一个请求约 0.15 秒，之后每个请求几毫秒。
- 停下来时回 `status: "decide"`：
  - `question`：第几个决定、第几回合、问什么，以及能选什么（每个带按钮文字，例如"快招 Bubble""大招 Ice Beam（55 能量）""换上 Medicham""什么都不做""开盾"）；
  - `sides`：双方的盾、换人冷却、在场的是谁，每只的 HP、能量、能力等级、快招，每个大招够不够、还差几次快招（`fast_needed`）；
  - `damage`（出招的问题里）：双方在场的两只之间，我方每个大招从 25% 到 100% 每 1% 的伤害、打死至少要几 %（`ko_min`）、不打死最多几 %（`survive_max`），双方快招一次的伤害，对方每个大招满蓄力的伤害。都是引擎的伤害函数算的，网页的拖动条只是查表；
  - `events`：到现在为止结算过的事件，不含双方的决定和原因，招式事件里开盾的原因也去掉（4c-2 补的）——对方的打算不能提前看到，打完以后在报告和时间线里看；
  - 开盾的问题里不告诉玩家是哪一招：对方的大招还没结算，事件里没有它；对方在场那只的能量显示这一回合开始时的值（实际的能量已经扣掉了大招的能量，看了就知道是哪一招）。
- 打完时回 `status: "finished"`：`result` 和打一场的结果一样（过程图、对位分段、带原因的时间线、报告），玩家那一队的策略写"玩家手动操作"。

**测试**：`tests/test_manual.py`（等待：不出招、能量不变、每回合再问、对手照常出招、时间线；威力：伤害按威力算、开盾时看到满蓄力的伤害、超出范围报错、下限可以改；手动对战：照 TeamPolicy 的选择一步步点，双方各试一次，打出来和自动对战完全相同，而且每一步停下来问的正好是下一个决定；第一个问题；重打是确定的；开盾的问题；不开盾、放不满的大招；各种写错的决定；报告），`tests/test_web_api.py`（第一个问题的内容、还差几次快招、伤害表和打死的门槛、事件里不含决定、开盾时不透露是哪一招、打完的结果、写错的请求、建配置的缓存），`tests/test_web_server.py`（接口）。

**页面（4c-2）**：和"打一场"在同一页，用上面填好的两队（开始时的配置存下来，之后改队伍不影响进行中的这一场）。
- 入口：按钮区"手动对战：我操作 [哪一队]"、"开始手动对战"；浏览器记住进行中的手动对战（配置、哪一方、到现在的决定），刷新页面后"继续上次的手动对战"。
- 对战区：
  - 上面是双方的状态（你在左边，对方在右边）：在场那只的圆形标记（底色是第一属性的颜色，边框是第二属性的颜色，写名字的前两个字母），HP 条，能量条（每个大招的能量处有刻度），能力等级，快招，每个大招"够了"或"还差 N 次快招"；盾、换人冷却、后备的 HP 和能量。对方的能量和大招也全部显示（测试环境，14.1）。
  - 中间是问题：
    - 出招：快招（默认）、什么都不做、换上每一只后备；每个大招一行，能量够的有威力拖动条（25%–100%，默认 100%），旁边实时显示"威力 X% → 打 D，对方 HP h → h−D"，按钮"不打死最多 Y%""打死至少要 X%""100%"把拖动条设到那里；能量不够的写还差几次快招。下面一行写双方快招一次打多少、对方每个大招满威力打你多少；对方还有盾时提醒"开盾的话只打 1，对方判断开不开盾时看的是满威力的伤害"。
    - 开盾：醒目地提示"对方放大招了！开盾吗？"，不说是哪一招，提醒"看对方的能量判断它放的是哪一招"；开盾 / 不开盾。
    - 不花回合的换人：不换 / 换上每一只后备。倒下后：换上哪一只。
  - 下面是战况：最近 14 个结算过的事件，刚才发生的高亮。
- 动画：刚才挨了快招的标记抖一下，飘出伤害数字；挨了大招的抖得更久、闪一下红光；换上来的淡入；倒下的变灰。
- 快捷键：回车或空格 = 快招（或"不换"），W = 什么都不做，Y / N = 开盾 / 不开盾，Backspace = 撤销上一步。另有"撤销上一步""从头再打""结束手动对战"三个按钮。撤销就是去掉最后一个决定再重打（不播放动画）；打完以后也能撤销。
- 打完以后：对战区写结果，下面接着显示和"打一场"一样的完整结果（过程图、对位分段、对方每个决定的原因、下载报告），玩家那一队的策略写"玩家手动操作"。
- 页面只负责显示和把你点的选项发回去：能选什么、伤害、还差几次快招都是服务器算的。JS 不加测试框架（14.1），在浏览器里从头到尾打过：出招、拉低威力放大招、开盾提示（不透露招式）、不开盾挨大招的动画、撤销回到开盾的问题、刷新后接着打、打完的结果、打完以后撤销、什么都不做。

### 14.6 能力值排序（4d）
需求见 14.1。单独一页 `web/stats.html`（两页顶上有切换），用的接口是 `GET /api/stats?league=1500&season=pvpoke&custom=a.toml`。

**每只怎么算**（`pogo_sim/stat_table.py`）：
- 每只按赛季规则建配置（`season.season_build`，和网页、配置文件里不填 IV、等级时一样）：IV 取这个联盟 IV 排名第 1，等级取等级上限内 CP 不超过联盟上限的最高等级，Mega 按赛季规则自动降等级。所以换赛季规则只会改 Mega 的等级（例如"Mega 提到 55"时大师联盟的 Mega 是 55 级）。
- 攻、防乘暗影倍率（`BattleRules.shadow_attack` 1.2、`shadow_defense` 0.83333331），和对战里算伤害时一样；HP 不变；脱壳忍者 HP 固定 10（和 `make_combatant` 共用 `combatant.species_stats`）。
- 坦度 = 防 × HP；能力值乘积 = 攻 × 防 × HP（含暗影倍率；IV 排名用的乘积不含暗影倍率，但同一只的每个 IV 组合乘的倍率一样，不影响谁排第 1）。
- 在这个联盟没有合法配置的（最低等级时 CP 就超过上限，例如超级联盟的 Darkrai，15 级时 CP 就超过 1500）不在表里，表上方列出名字和原因。

**速度和缓存**：找 IV 排名第 1 要把 4096 个 IV 组合都算一遍，全部 1753 只单进程约 39 秒。
- 多进程并行算（标准库 `concurrent.futures.ProcessPoolExecutor`，进程数默认是 CPU 核数，每个进程自己读 gamemaster）：在 14 核的机器上约 4 秒。要算的不到 40 只时不开多进程。
- 算出来的等级和 IV 存进 `.cache/stat_table/<联盟>_<赛季规则>.json`（不入库），之后读缓存约 0.02 秒。
- 每只记下算它用到的数据（种族值、levelFloor、tags）：数据变了（比如覆盖文件改了种族值、新加了宝可梦）只重算那几只；算等级和 IV 的代码（`cpm.py`、`stats.py`、`iv_ranking.py`、`season.py`、`combatant.py`、`stat_table.py`）改了，整个缓存作废；文件坏了当没有。
- 同时来两个请求时一个一个算（第二个等第一个算完，直接读缓存）；写缓存先写临时文件再改名。

**页面**（`web/stats.js`）：
- 设置：联盟、赛季规则、覆盖文件（和打一场那页一样）。
- 筛选：排除 Mega、传说、幻之、究极异兽、暗影（gamemaster 的 tags）；只看已实装；属性；只看 PvPoke 排名前 N（Mega 看 Mega 版排名）；搜名字（和选宝可梦的下拉框一样的搜法）。覆盖文件里的宝可梦总是列出（不看"只看已实装"和"排名前 N"，其余筛选照常），整行标黄，方便看新宝可梦排在哪。
- 表：宝可梦、PvPoke 排名、CP、等级、IV、攻、防、HP、坦度、能力值乘积（千）、自定义、种族攻 / 防 / HP。点表头排序，再点一次反过来；名字和排名第一次点从小到大，其余从大到小。默认按坦度从高到低。一次显示 200 行，下面有"再显示"。
- 自定义一列：攻^a × 防^b × HP^c，a、b、c 自己填（可以是小数、0、负数），显示成占筛选后第 1 名的百分比；两个按钮直接设成坦度（0, 1, 1）或能力值乘积（1, 1, 1）。
- 设置、筛选、排序和公式记在浏览器里（localStorage）。
- 每只的数都是 Python 算好发过来的；网页只做筛选、排序和自定义一列的乘方（只是显示）。

**测试**：`tests/test_stat_table.py`（等级和 IV 和 `season_build` 一样、Mega 降等级、暗影倍率、脱壳忍者、没有合法配置的、未知的赛季规则；缓存：第二次不再算、新加或数据变了的只算那几只、代码改了全部重算、坏文件当没有；多进程和单进程结果相同），`tests/test_web_api.py`（接口的每一行和网页上建一只的配置一样、宝可梦的说明和宝可梦列表一样、没有合法配置的、暗影倍率、第二次读缓存、写错的联盟 / 赛季规则 / 覆盖文件），`tests/test_web_server.py`（页面文件、写错时回 400）。测试只算几只，缓存放在临时目录。页面在浏览器里核对过：超级联盟第一次 3.9 秒、之后读缓存；按名字、坦度、自定义排序；排除和排名前 50；勾上覆盖文件只新算 1 只、Mega 雪妖女和 Mega 基格尔德标黄；换到大师联盟、换赛季规则。

**同时做的小改动**：两页共用的小工具（`el`、`select`、`api`、属性颜色、搜索的规范化）从 `app.js` 挪到 `web/common.js`。

### 14.7 搜索应对（4e）
需求见 14.1，方法见 13.11（逐步试探）。在"打一场"页，用的是上面填好的两队。

**引擎**（`pogo_sim/best_response.py`，搜索的方法和结果不变）：
- 搜索时记下试过的每个决定点（`Tried`：决定点、每个选项打出来的结果、搜索后的选择、试之前和试之后的结果），不只是改了的。`BestResponse.tried` 是全部，`changes` 是其中改了的，`examined` 是个数。
- 试过的决定点正好是搜索后那一场里有不止一个选项的决定点（按顺序）：前面的决定不变时，前面的局面也不变（测试里核对）。
- 决定点另记下做决定时在场的是第几只（`DecisionPoint.active`），网页上写"快招 Bubble"时要知道是哪一只的快招。
- 报告多了"试过的全部决定点"一节（13.11 第 4 条）；`docs/experiments/gl_3v3_best_response.md` 重新生成，只多了这一节（用时那个数每次不同）。

**接口** `POST /api/best-response`：请求是 `{"config": 和打一场一样的配置, "side": 搜哪一方}`，同一个配置只建一次两队（和手动对战共用缓存）。例子约 0.5 秒（Team A，打 50 场）到 2 秒（Team B，105 场），同步等结果。返回：
- `search`：搜的是哪一队、对手；原策略和搜索后的结果（胜负、评分、一行中文结果）；一共几个决定、试过几个、改了几个、打了几场、用时；
- `tried`：试过的每个决定点，按搜索的顺序：回合、种类、原策略的选择、搜索后的选择、改没改、试之前和试之后的结果，以及每个选项（文字、结果、是不是原策略的选择、是不是搜索后的选择）。选项的文字和手动对战的按钮一样（"快招 Bubble""大招 Ice Punch""换上 Medicham""开盾""不换"）；
- `result`：搜索后的这一场，内容和打一场一样（过程图、分段、带原因的时间线……）。搜索的那一队，策略写"逐步试探搜索出来的打法；原策略（起点）是 TeamPolicy，……"；报告是 best-response 的完整报告，和命令行 `--best-response` 一样（网页没有说明文字，所以开头少那一段）；
- `baseline`：原策略那一场，和打一场打出来的完全相同。

**页面**：
- 按钮区"搜索应对：搜 [哪一队] 的打法"、"搜索"。
- 结果最上面是"搜索应对"：方法的说明；原策略和搜索后的结果；决定数、试过几个、改了几个、打了几场、用时；"下面显示：搜索后的这一场 / 原策略那一场"两个按钮，下面的过程图、分段、时间线等跟着换。
- "改了哪些决定"表：改1、改2……，回合、决定、原策略、改成、改之前 → 改之后、各选项打出来的结果（每个选项一个小块：绿是赢、灰是平、红是输；粗框是搜索后选的；原策略的选择标"原策略"）。点一行跳到时间线的那一回合。
- "试过的全部决定点"默认折起来，展开后每个决定点一行，改了的标绿。
- 看搜索后的这一场时，过程图上改了的决定画绿色虚线（写"改1"……），时间线里那几回合标绿；改过的决定的原因写成 `best response: …（policy would …）`。
- 下载的报告：搜索后的这一场是 best-response 的报告，原策略那一场是普通的 3v3 报告。
- 打一场或手动对战打完时，搜索应对的结果清掉。

### 14.8 保存队伍（4f）
需求见 14.1。两部分：队伍库（一队一个文件）和"打一场"页的配置文件导入 / 导出。九宫格、队伍对队伍两页的导入导出跟着那两页做（4g、4h）。

**写 TOML**（`pogo_sim/toml_writer.py`）：标准库 `tomllib` 只能读，自己写了一个只支持配置里用到的写法的 `dumps`（字符串、整数、小数、真假、列表、表、表的列表，可以嵌套），不加依赖。一个表里先写普通的键，再写子表，最后写表的列表。测试里写出去再读回来核对，包括仓库里的几个配置文件。

**队伍库**（`pogo_sim/team_library.py`，格式写在模块开头）：
- 放在仓库的 `teams/`，入库（`teams/README.md` 说明）。一队一个文件：`league`（常用联盟，只用来筛选，载入时不强制）、可选的 `custom_files`（用到的覆盖文件，`data/custom/` 里的文件名）和 `note`，然后是 `[team]`。`[team]` 和 3v3 配置里的一个 `[[team]]` 写法相同，检查也相同（`team_battle.parse_team`）。
- 文件名由队名得到：字母、数字（含中文）、下划线、点、减号以外的字符都换成下划线，例如 "Team A (Mega Froslass)" → `Team_A_Mega_Froslass.toml`（空格、括号在命令行里要转义）。
- 读库：`teams/*.toml` 按文件名；读不了的文件单独列出原因，不影响其他队伍。手写的文件也行。
- 存：先不覆盖；同名的已经有了，网页问过再带 `overwrite` 重发。写之前核对写出来的文本能原样读回来，先写临时文件再改名。**没有删除**（14.1）。
- 用到的覆盖文件（`custom_files_used`）：存的时候勾着的覆盖文件里，新加或修改了这一队某一只的宝可梦或者某个招式的（`custom.touched_ids` 只看覆盖文件里各表下面的 ID）。例如勾着三个覆盖文件存带 Mega 雪妖女的队伍，只记 `mega_froslass.toml`。

**接口**：
| 接口 | 做什么 |
|---|---|
| `GET /api/team-library` | 库里的全部队伍（文件名、队名、联盟、用到的覆盖文件、说明、`[team]` 的内容、网页上改不了的策略参数）和读不了的文件 |
| `POST /api/team-library/save` | `{league, season, custom_files, team, note, overwrite}`：先和打一场一样检查、建一遍配置（建不了的不让存），再存。同名的已经有了又没带 `overwrite` 时不写，回 `saved: false` 和已有的那一队 |
| `POST /api/export-config` | 页面上的配置写成 3v3 配置文件：先和打一场一样检查，覆盖文件写成 `data/custom/` 下的路径，开头注释写运行命令。回建议的文件名（`3v3_队名_vs_队名.toml`）和内容 |
| `POST /api/import-config` | `{text, name}`：检查和命令行读配置文件完全相同（`parse_team_battle_config`），覆盖文件只能是 `data/custom/` 里的。网页上用不上的（说明文字、`[rules]`、盾数和 `switching` 以外的策略参数）不导入，写在 `warnings` 里；共用的 `[policy]` 里的 `switching` 合并到每一队 |

**页面**（"打一场"页）：
- 设置里一行"3v3 配置文件：导入… / 导出"。导出下载文件；导入选一个文件，确认（列出没导入的设置）以后换掉现在的设置和两队。
- 每队旁边"存进队伍库"（问一句说明，可以留空；同名的先问再覆盖，提示里写已有的那一队）和"从队伍库载入"。载入的面板：只看现在的联盟（可以取消）、搜队名 / 宝可梦 / 说明，每队一行（队名、联盟、文件名、成员、说明、用到的覆盖文件、"载入到 某队"），下面列出读不了的文件。
- 载入时：用到的覆盖文件没勾的自动勾上；联盟不同只提示（按现在的联盟建配置）；网页上改不了的策略参数提示没载入。状态栏写明这些。

**测试**：`tests/test_toml_writer.py`（各种值、表和表的列表、写法的顺序、要加引号的键、写不了的值、仓库里的配置文件写出去再读回来），`tests/test_team_library.py`（文件名、写出去读回来、写错的文件、存和覆盖、不留临时文件、读不了的文件单独列出、用到的覆盖文件），`tests/test_web_api.py`（存进库、同名不覆盖和覆盖、只记用到的覆盖文件、建不了的不让存、列出库、导出的文件命令行能跑而且打出来和页面上的一样、导入例子文件得到例子配置、导出再导入不变、导入时用不上的设置写进 warnings、写错的文件），`tests/test_web_server.py`（四个接口）。测试里的队伍库都放在临时目录。页面在浏览器里核对过：库是空的时的提示；存、同名再存（问过再覆盖）；存带 Mega 雪妖女的队伍（只记 `mega_froslass.toml`），取消勾选以后载入（自动勾上）；换到高级联盟载入超级联盟的队伍（提示不强制）；导出再导入。核对时存进 `teams/` 的测试队伍已经删掉。

### 14.9 1v1 九宫格和环境前 N（4g）
需求见 14.1。和命令行 `tools.run_matchups` 是同一套配置（12.2、13.9）和计算。分两个单元：4g-1 是接口和两页共用的页面代码，4g-2 是页面（`web/matchups.html`、`web/matchups.js`）。

**4g-1：接口**（`web_api.py`）：
- 网页发来的配置和九宫格配置文件写法一样、键也一样，走同一套检查：`matchups.py` 的 `load_matchup_config` 拆出 `parse_matchup_config(raw, where)`（同 4a 对 3v3 的做法），命令行的行为不变。覆盖文件只能从 `data/custom/` 里选，写文件名。
- 建环境前 N 花时间（每只要算 IV 排名，前 50 只约 1 秒），所以服务器缓存建好的环境前 N（`cached_pool_builder`，最多 32 组）。键是覆盖文件的路径和修改时间、这一组的设置（名字除外）、联盟、赛季规则；只改了名字时用建好的，换上新名字。为此 `prepare_matchups` 多了参数 `build_pool`（默认 `rankings.prepare_pool`），网页传进带缓存的。整个建好的配置也按配置本身缓存（同 `prepared_battle`），点一格看一场时不用重建。实测：例子配置第一次 2.1 秒（1620 场，含建 60 只的环境前 N），只改测试对象 0.26 秒。同步请求就够，流式进度留给 4h。

### 14.10 队伍对队伍（4h）
需求见 14.1。和命令行 `tools.run_team_matrix` 是同一套配置（13.10）和计算。分两个单元：4h-1 是接口、流式进度和测试，加上把一队的编辑器抽成共用；4h-2 是页面（`web/matrix.html`、`web/matrix.js`）。

**4h-1：引擎这边**（`team_matrix.py`，命令行的行为和报告不变）：
- `load_team_matrix_config` 拆出 `parse_team_matrix_config(raw, where)`，网页发来的配置走同一套检查（同 4a、4g 的做法）。
- `prepare_team_matrix`、`draw_sample` 多了参数 `build_pool`（建抽样候选的函数，默认 `rankings.prepare_pool`），网页传进带缓存的，和九宫格共用同一个缓存。这个函数的类型 `PoolBuilder` 从 `matchups.py` 挪到 `rankings.py`。
- 新加 `iter_team_matrix`：一场一场地打，每打完一场给出 `(我方第几队, 对手第几队, 结果)`；不再往下取就不再打。`run_team_matrix` 改成用它。
- 对手分组（手写 / 抽样 / 全部）改成公开的 `opponent_groups`，报告和网页的总表共用。
- `config.py` 新加 `entry_table`：`parse_entry` 反过来，一只写成配置里的表（`parse_entry(entry_table(e)) == e`）。随机抽的队伍送到"打一场"页时用。

**4h-1：边打边发进度**：
- `web_api.team_matrix_stream(raw)` 先检查、建好每一队、抽好样（写错时直接报错，服务器回 400，还没开始发），再返回一个迭代器：开始（一共几场、每队的配置、抽样的说明和候选）→ 每隔 0.2 秒一批打完的结果（`MATRIX_PROGRESS_SECONDS`，按打的顺序）→ 结束（总表、和命令行相同的报告和 CSV、花了几秒）。
- 服务器（`tools/run_web.py`）的 `STREAM_API` 把每一项写成一行 JSON（NDJSON，`application/x-ndjson`），写完一项就发出去；响应没有 Content-Length，发完就关连接。网页点"停止"就是断开请求：服务器写不出去，就关掉迭代器，后面的也就不再打（测试里核对）。发到一半出了意外错误时，最后一行是 `{"type": "error", ...}`。
- 实测：例子配置（我方 2 队 × 对手 51 队）建配置 1.1 秒，102 场 3.4 秒；进度每 0.2 秒一批，大约 17 行。

| 接口 | 做什么 |
|---|---|
| `GET /api/matrix-options` | 随机抽能选什么（同九宫格的环境前 N）、打开"随机抽"时先填的值、例子配置（`experiments/gl_team_matrix_example.toml`） |
| `POST /api/team-matrix` | 跑队伍对队伍，边打边发（见上） |
| `POST /api/matrix-battle` | `{config, team, opponent}`（从 0 数起；对手手写的在前、抽样的在后）：这一场完整的 3v3 结果，结构和 `/api/team-battle` 相同，含完整报告；和命令行 `--battle` 打的是同一场 |
| `POST /api/matrix-pairing` | 同上的请求：把这一场写成"打一场"页的配置（两队都写成每只的配置，随机抽的也一样），打出来和这里同一场；"打一场"页改不了的策略参数写进 `warnings` |
