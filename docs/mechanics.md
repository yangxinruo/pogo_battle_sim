## 2. 数值：CP、能力值、等级

### 2.1 等级与 CPM
- 等级 1 到 55，步长 0.5，共 109 个 CPM 值。PvPoke 直接查表，半级也在表里。
- 来源：`pokemon/Pokemon.js` 第 24 行 `cpms` 数组，`getCPMByLevel`（第 2026 行）。
- 状态：**参考 PvPoke**（1–51 级的值与游戏公开数据一致；51 级以上未独立核对）。
- 默认等级上限 50（`Battle.js` 第 11 行 `levelCap = 50`）。

### 2.2 实际能力值
```
攻击 = CPM × (种族攻击 + 攻击IV)          不取整
防御 = CPM × (种族防御 + 防御IV)          不取整
HP   = max(floor(CPM × (种族HP + HP IV)), 10)
```
- 来源：`Pokemon.js` `initialize`，第 380–382 行附近。
- 状态：**参考 PvPoke**。攻防保留小数这一点会影响伤害的断点，所以单独写明。
- 特例：脱壳忍者（dex 292）HP 固定为 10。

### 2.3 CP
```
CP = max(floor((攻+IV) × sqrt(防+IV) × sqrt(HP+IV) × CPM² / 10), 10)
```
- 来源：`Pokemon.js` `calculateCP`（第 425 行）；最低 10 在 `initialize` 里。
- 状态：**已验证**（见 `tests/test_stats.py`，与游戏内已知 CP 一致）。

### 2.4 联盟默认等级和 IV
- gamemaster 每只宝可梦有 `defaultIVs`，例如 `"cp1500": [等级, 攻IV, 防IV, HP IV]`。PvPoke 默认用这组值（`Pokemon.js` `initialize` 的 `"gamemaster"` 分支）。
- 无上限联盟（CP 10000）：15/15/15，等级取上限。
- 状态：**参考 PvPoke**。这是 PvPoke 的默认选择，不是游戏规则。

### 2.5 正作能力值换算（用于未发布宝可梦）
公式见 CLAUDE.md，已实现在 `pogo_sim/conversion.py`。
- 状态：**已验证**。11 只非 Mega（含 5 只触发 0.91 削弱的）和 50 只 Mega（含 5 只触发 0.97 削弱的）的换算结果与 gamemaster 完全一致。见 `tests/test_conversion.py`。
- 实现细节一：四舍五入用"0.5 进位"，不能用 Python 内置的 `round`（它是银行家舍入，遇到 .5 会出错，例如 Mega 超梦Y 的防御中间值 202.5）。
- 实现细节二：**削弱倍率要乘在最后一次取整之前**，不是对取整后的种族值再乘。CLAUDE.md 写的"三项乘 0.91"没有区分这两种做法，对照数据后确定是前者：
  - 请假王防御：round(174 × 1.05 × 0.91) = 166（游戏值）；先取整再乘会得到 167。
  - 雷吉奇卡斯 HP：round((1.75 × 110 + 50) × 0.91) = 221（游戏值）；先向下取整再乘会得到 220。

**两条削弱规则**（都按"只套公式的结果在 15/15/15、40 级的 CP"判断）：

| 适用 | 门槛 | 倍率 | 状态 |
|---|---|---|---|
| 非 Mega | CP ≥ 4000 | 0.91 | 已验证 |
| Mega / 原始回归 | CP ≥ 6000 | 0.97 | 倍率已验证；门槛待确认（数据只能限定在 5425–6039 之间） |

- Mega 削弱的依据：用户确认 Mega 超梦X/Y、Mega 烈空坐、原始固拉多/盖欧卡在游戏里都是 0.97 倍（2026-11-17 答复 Q2）。PvPoke 数据里恰好是这 5 只乘了 0.97，CP 最高的不削弱者是 Mega 烈咬陆鲨（5424），最低的削弱者是 Mega 烈空坐（6039）。
- 不是按"是否传说"划分：Mega 拉帝亚斯 / 拉帝欧斯（传说，4801 / 5007）和 Mega 蒂安希（幻之，4346）都没有削弱。
- 门槛是 `pogo_sim/conversion.py` 里的 `MEGA_NERF`，可以传自己的 `NerfRule` 试别的假设。将来出现 CP 落在 5425–6039 之间的新 Mega，就能定下准确门槛。
- Mega 超梦X：只套公式 412/222/235，削弱后 399/215/228（游戏值）。

## 3. 伤害

### 3.1 公式
```
伤害 = floor(0.5 × 威力 × (攻击/防御) × STAB × 克制倍率 × PvP加成 × [Mega招式加成] × [蓄力比例]) + 1
```
- 来源：`battle/DamageCalculator.js` `damage`（第 68 行）。
- 状态：**参考 PvPoke**，公式本身与社区公认一致。实现在 `pogo_sim/damage.py`，已用 PvPoke 源码逐位核对（见 3.6）。
- 乘法顺序照搬 PvPoke：`威力 × STAB × (攻/防) × 克制 × 蓄力 × Mega加成 × 0.5 × PvP加成`。浮点乘法不满足结合律，理论上换顺序可能在取整边界上差 1；实际搜索 40 万个随机组合没有找到这样的例子，但仍保持一致。

### 3.2 各倍率
| 倍率 | PvPoke 的值 | 说明 |
|---|---|---|
| PvP 加成 | 1.2999999523162842 | 即 float32 的 1.3 |
| STAB | 1.2000000476837158 | float32 的 1.2 |
| 效果绝佳 | 1.600000023841858 | float32 的 1.6 |
| 效果不好 | 0.625 | |
| 无效（双重抵抗同值） | 0.390625 | |
| 暗影攻击 | 1.2 | 乘在攻击上 |
| 暗影防御 | 0.83333331 | 乘在防御上 |
| Mega 招式加成 | 1 / 1.1 / 1.2 / 1.3 | 对应 Mega 等级 1–4，只对标记 `isMegaMove` 的招式生效，见第 7 节 |

- 来源：`DamageCalculator.js` 第 2–11 行 `DamageMultiplier`。
- 状态：**参考 PvPoke**。PvPoke 特意用 float32 精度的常数（2025-05 的两次提交 "fix: damage constant floating points"），说明这些精度会影响边界情况下的取整，我们照搬。
- 双属性：两个属性的倍率相乘（`getEffectiveness`，第 140 行）。

### 3.3 攻击和防御用什么值
```
有效攻击 = 攻击 × (能力等级倍率 × 暗影攻击倍率)
有效防御 = 防御 × (能力等级倍率 × 暗影防御倍率)
```
（PvPoke 先把两个倍率相乘，再乘到能力值上。）
- 暗影宝可梦在 gamemaster 里是单独的条目（如 `azumarill_shadow`，带 `shadow` 标签），PvPoke 据标签设置暗影倍率（`Pokemon.js` 第 406 行）。
- 来源：`Pokemon.js` `getEffectiveStat`（第 2091 行）。
- 状态：**参考 PvPoke**。

### 3.4 被盾挡下
- 伤害变为 1（`Battle.js` 第 1199 行）。
- 状态：**参考 PvPoke**，与 CLAUDE.md 里"待确认"的说法一致。

### 3.5 蓄力比例
- 模拟模式固定为 1（满蓄力）。只有训练对战里玩家手动蓄力时才小于 1。
- 我们的引擎可以先固定为 1，留一个参数。

### 3.6 与 PvPoke 源码的核对
`tools/pvpoke_ref/` 在 Node 里运行 PvPoke 源码（commit `d02018e`），生成 `tests/fixtures/pvpoke_damage_reference.json`：
- CPM 表 109 项、属性克制 3078 项（18 种招式属性 × 171 种防守属性组合）：逐位相同。
- 伤害用例 428 个（28 个手挑 + 400 个随机）：CP、有效攻防、克制倍率、STAB、最终伤害全部逐位相同。
- 手挑用例覆盖：双重弱点/抵抗、免疫、免疫×弱点、暗影攻守、能力等级 ±4、Mega 等级 1–4、威力 0、51 级。
- 其中 4 个是"float32 边界"用例：如果把 1.3 / 1.2 / 1.6 换成精确值，这 4 个的伤害会差 1，说明照搬 float32 常数确实有影响。
- 反向检查：故意改错暗影倍率、能力等级公式、STAB、Mega 加成，分别有 190、253、171、3 个用例失败，说明这套用例能发现这类错误。

暂不支持（形态变化留到以后）：Gulp Missile（按对手最大 HP 百分比算伤害）、Aegislash 等 11 个有形态变化的宝可梦的特殊规则。

## 5. 回合结构与结算顺序

这一节是 PvPoke 现在的实现（`Battle.js` `step`，第 284–612 行）。与官方说明的逐条对比在 5.4。
本项目的实现在 `pogo_sim/battle.py`（以回合为单位，冷却记作"还要等几回合"，与 PvPoke 的毫秒一一对应），已用 PvPoke 源码逐回合核对，见 5.5。

### 5.1 一个回合里发生什么
1 回合 = 500ms。每回合按下面的顺序：

1. **冷却减少**：双方 `cooldown` 各减 500ms，最低 0。换人计时器同样减 500ms。
2. **决定行动**：对 `cooldown == 0` 的宝可梦，决定本回合行动（快招 / 大招 / 换人）。
   - 如果**上一回合有大招结算**，本回合只接受换人，其他行动直接丢弃（第 341 行）。
   - 快招：冷却加上招式时长，放入队列。
   - 大招：冷却加 500ms，放入队列。
   - 决定行动时双方都用回合开始时的状态，互相看不到对方本回合的选择。
3. **从队列取出本回合要结算的行动**（第 397–431 行）：
   - 快招：在它的**最后一个回合**结算。即 N 回合的快招在第 T 回合开始，则在第 T+N−1 回合结算。
   - 例外："漂浮"的快招：如果上一回合有大招结算，所有在更早回合开始、还没结算的快招都在本回合立刻结算。
   - 大招：在放入队列的当回合结算。
   - 换人：当回合结算。
4. **按优先级从高到低依次执行**（第 434 行）。优先级：

   | 行动 | 优先级 |
   |---|---|
   | 换人 | +20（如果是大招后的 0 回合换人，再 −40，排到最后） |
   | 大招 | +10；攻击高于对手再 +1 |
   | 快招 | 0 |

   模拟模式下双方基础优先级都是 0；优先级相同时保持原顺序（0 号在前）。
5. **执行时的有效性检查**（第 449–493 行）：
   - 快招：对手已倒下则无效；自己已被**大招**打倒则无效。被快招打倒不影响。
   - 大招：能量够才有效；如果双方攻击不同（有先后手），后手被对方大招打倒则无效。
   - 换人：冷却为 0 且换人计时器为 0，或自己已倒下。
6. **回合结束**：检查倒下。如果本回合有大招结算，双方冷却都设为 500ms（第 548 行）。

### 5.2 大招的时序
综合上面的规则，一次大招是这样的：

| 回合 | 发生什么 |
|---|---|
| T | 攻方决定放大招。大招伤害和效果在本回合结算，先于本回合的快招。 |
| T+1 | "空回合"。双方不能出新招。之前没结算完的快招（漂浮）在这里结算。可以 0 回合换人。 |
| T+2 | 恢复正常，双方都可以行动。 |

所以放一次大招占 2 个回合。8 月更新之前只占 1 个回合，这是新系统带来的主要变化。

**大招期间的快招（Sneak 和 Leak）**：
- 对手在 T 回合才开始的快招（不管几回合长），在 T+1 结算，然后对手在 T+2 就能自由行动。相当于白拿了这个快招剩余的时长。
- 对手在 T 之前开始、原本要在 T 之后才结算的快招，同样在 T+1 结算，剩余时长作废。
- 对手原本就该在 T 回合结算的快招，在 T 回合大招之后结算；如果它被这个大招打倒了，这个快招不生效。

### 5.3 同回合的各种情况
- **双方同回合快招结算**：都生效，包括其中一方（或双方）因此倒下。
- **双方同回合放大招**：攻击高的先结算。先手打倒后手，后手的大招不生效。攻击相同时双方的大招都生效，即使被打倒。
- **一方大招、一方快招同回合结算**：大招先。被大招打倒的一方，快招不生效。
- **自己本回合会被快招打倒，同时放大招**：大招先结算，所以大招照常生效。

### 5.5 与 PvPoke 源码的核对
`tools/pvpoke_ref/export_battle_reference.js` 在 Node 里运行 PvPoke（commit `d02018e`），生成 `tests/fixtures/pvpoke_battle_reference.json`：
1. 让 PvPoke 的 AI 模拟一场；
2. 用 PvPoke 自己的沙盒模式（`setSandboxMode(true)`）把这场转成剧本：哪一回合放哪个大招、守方开没开盾、概率性能力变化有没有触发。其余回合一律快招；
3. 按剧本重放并逐回合记录双方的 HP、能量、冷却、能力等级、盾数。脚本会检查重放结果与第 1 步完全相同（52 场全部相同），说明剧本完全决定了对战。

`tests/test_battle_pvpoke.py` 用同一个剧本驱动我们的引擎（`ScriptedPolicy`），比较每一回合的状态、每一次招式的伤害和开盾、最终评分、回合数和对战时间。
- 覆盖：16 个对局 × 多种盾数，共 52 场、2022 个回合。包括 1/2/3/4/5 回合的快招、必定和概率性的能力变化（Power-Up Punch、Close Combat、Brave Bird、Icy Wind、Lunge、Obstruct、Night Slash、Ancient Power、Moonblast）、暗影、CMP 平手的镜像、超级联盟、大师联盟的 Mega 第三个大招。
- 结果：全部逐回合相同。
- 反向检查（故意改错一条规则，看多少场对不上）：去掉大招后的空回合 48 场、快招早一回合结算 49 场、大招后不重设冷却 23 场、快招先于大招 19 场、被大招打倒后快招仍生效 17 场、挡盾后不降对手能力 3 场、CMP 平手改随机 3 场、去掉漂浮快招 3 场、CMP 改用有效攻击 1 场。每条规则都至少有一场能发现错误；漂浮快招这条覆盖偏少，因为 PvPoke 的 AI 会把大招卡在对手快招刚结束时放，另外在 `tests/test_battle.py` 有单独的测试。
- `tests/test_battle.py` 另有每条规则一个的小场景测试（同回合快招互相打倒、大招先于快招、CMP、大招占两回合、Sneak、挡盾、计数器、240 秒时限等），不依赖 PvPoke 数据。

## 6. 盾、CMP、能力变化、换人

### 6.1 盾
- 每方 2 个（`pokemon/Player.js` 第 20 行）。3v3 中全队共用。
- 挡下后伤害为 1。
- **被挡下的大招，附带的能力变化仍然生效**，包括对对手的削弱。代码里有一段注释写着"挡下就不削弱"，但实际没有起作用（`Battle.js` 第 1231–1233 行把修正值设成了 0，等于什么都没做）。
- 状态：**参考 PvPoke**。挡盾后削弱仍生效这一点与我对游戏的了解一致，但请确认（Q6）。

### 6.2 CMP（同回合大招的先后）
- 比较的是**不含暗影加成、不含能力等级**的攻击（`stats.atk`，即 CPM × (种族值 + IV)）。来源：`Battle.js` 第 262、783 行。
- 攻击高者先手。
- 攻击相等：没有先后，双方大招都生效（`usePriority = false`）。
- 状态：攻击高者先手 **参考 PvPoke**；攻击相等的处理 **待确认 Q8**（用户印象是游戏里随机决定先后，与 PvPoke 不同）；比较时是否不含暗影和能力等级 **待确认**。
- 引擎里做成开关：`PvPoke 方式（双方都生效）` / `随机先后（可设种子）`，默认 PvPoke 方式，方便对照。

### 6.3 能力等级
- 攻击和防御各自 −4 到 +4 级（gamemaster `settings.maxBuffStages = 4`，`buffDivisor = 4`）。
- 倍率：等级 s > 0 时为 (4 + s) / 4；s ≤ 0 时为 4 / (4 − s)。即 4/8 到 8/4。
- 来源：`Pokemon.js` `getStatBuffMultiplier`（第 2113 行）、`applyStatBuffs`（第 2077 行）。
- 状态：**参考 PvPoke**，与 CLAUDE.md 一致。
- 招式数据：`buffs: [攻击变化, 防御变化]`，`buffTarget: self / opponent / both`，`buffApplyChance`。`both` 时用 `buffsSelf` 和 `buffsOpponent`。
- 换下场时能力等级清零（`Battle.js` 第 996 行）。
- **概率性效果**：PvPoke 模拟模式不掷骰子。每个概率招式有一个计数器，初始值等于概率（50% 的招式初始为 0），每用一次加上概率，计数器每跨过一个整数就触发一次（`Battle.js` 第 1408–1417 行，`Pokemon.js` `resetMoves`）。
  例：12.5% 的 Night Slash 在第 7 次使用时触发；50% 的招式在第 2 次触发；10% 的招式在第 10 次触发（初始 0.1，用 9 次后浮点累计是 0.9999999999999999，不到 1）。
  计数器只给大招建；快招的概率效果在这个模式下从不触发（目前数据里没有带效果的快招）。
  这是 PvPoke 为了让结果可复现做的简化。见 Q7。实现：`BattleRules.chance_effects`，另有 `"random"` 选项；剧本可以逐次指定。

### 6.4 换人
- 换人冷却：45 秒（`Player.js` 第 22 行 `switchTime = 45000`；2025-09-04 提交 "Updated switch timer"）。主动换人时开始计时，倒下后的换人不触发。
- 大招期间换人冷却照常走（用户实战经验，Q13）。所以以回合为单位的引擎需要一个参数"每次大招折算成几秒"，数值待实测，3v3 阶段再定。
- 主动换人花 1 回合，倒下后换人和大招后换人不花回合（见 5.4）。
- 倒下后玩家有选择时间（PvPoke 训练模式里是 13 秒超时）。
- 状态：**参考 PvPoke**。
- **重要**：PvPoke 的普通模拟（Battle 页面、排名、矩阵）是纯 1v1，完全没有换人。换人只存在于训练对战模式。

### 6.5 胜负判定
- PvPoke 的 1v1 模拟在任一方倒下时结束，或时间超过 240 秒。
- "时间"的算法：没有大招的回合 +0.5 秒；有大招的回合按大招小游戏计 10 秒，同回合的第二个大招再加 10 秒（有盾时的计法略有不同，见 `battle.py` 的 `_end_of_turn_ms`）。只用快招时第 481 回合超时。状态：大招期间对战计时继续走——已验证（用户实战经验，2026-11-18），与 PvPoke 的做法一致；每次大招具体计多少秒（10 秒）参考 PvPoke。
- 对战评分 = floor(500 × 对手损失HP比例 + 500 × 自己剩余HP比例)，高者胜（`Pokemon.js` `getBattleRating`，第 2134 行）。
- 这是 PvPoke 的评分方式，不是游戏规则。我们的引擎可以输出同样的评分，方便对比。

## 7. Mega

PvPoke 目前的做法（都是 **参考 PvPoke**，其中多项它自己也说是暂定）：

- gamemaster 里 Mega 有 `mega` 标签（64 只），其中 19 只还有 `supermega` 标签。
- **Mega 等级**：默认 3；有 `supermega` 标签的默认 4（`Pokemon.js` 第 63、146 行）。
- **第三个大招**：所有 Mega 都可以带（`hasThirdChargedMove`）。额外招式在 `extraChargedMoves` 里，是带 "+" 的专属招式（如 `DYNAMIC_PUNCH_PLUS`）。
  - "+" 招式共 19 个，其中 18 个标记了 `isMegaMove`；**`MOONBLAST_PLUS`（Mega 皮可西）没有标记**，所以 PvPoke 不给它 Mega 加成。疑似 PvPoke 数据遗漏，见 9.2。
  - `extraChargedMoves` 里还有 Cramorant 的 Gulp Missile（形态机制，不是第三个大招）。所以"能带第三个大招"要按"是 Mega 且有 `extraChargedMoves`"判断。
- **Mega 招式加成**：`isMegaMove` 的招式伤害乘以 1 / 1.1 / 1.2 / 1.3，对应 Mega 等级 1–4（`DamageCalculator.js` 第 10、41 行）。依据是 PvPoke 2026-09-01 的更新说明 "Mega Move Update"。
- **Mega 等级 4 的等级上限**：等级上限从 50 提到 52（`Pokemon.js` 第 294 行，2026-09-02 提交 "Mega Level 4 CP Boost"）。
- **CP 超上限的 Mega**：PvPoke 直接按 `defaultIVs` 用一个很低的等级（例如 Mega 超梦X 在 1500 联盟是 9 级），当成普通的低等级宝可梦处理。
- **Mega 的属性加成**：PvPoke 没有实现。
- **每队几只 Mega**：PvPoke 的模拟是 1v1，不涉及；它的组队工具（`interface/TeamInterface.js` 第 817 行）在队里已有 Mega 时排除其他 Mega，即按每队 1 只处理。

用户 2026-11-17 的答复（Q9–Q11），本项目的做法：
- **Mega 等级 1–4 和专属招式加成是游戏正式机制**，照 PvPoke 实现。
- **等级上限做成可配置**，不写死 52。不同赛季规则不同，已知的有：Mega 等级上限固定 52；Mega 后自动提到 55；Mega 比普通上限多 2 级（加上挚友加成最高 53）。打算用"普通上限 + 挚友加成 + Mega 额外等级，或直接指定 Mega 上限"来表示。
- **第三个大招只有 Mega 能带**，按 gamemaster 里有 `extraChargedMoves` 的实现。普通宝可梦目前只有两个大招。
- **CP 超上限的 Mega**：给定 IV，取不超过 CP 上限的最高等级，做成可配置。
- 另外，挑选让实际战斗力最大的 IV（按攻×防×HP 的乘积排名）是一个单独的功能，放在路线图第 2 步（自定义宝可梦）里做。

用户 2026-11-18 的答复：
- **Mega 属性加成只在 Raid 生效，PvP 不生效**。Raid 里的数值是：与 Mega 同属性的招式 1.3 倍、其他属性 1.1 倍，作用于其他训练师的宝可梦，Mega 自己没有加成。引擎不实现这一项。
- **每队只能带 1 只 Mega**（正作基本也只允许一只）。3v3 组队时检查。
- 等级上限的几种赛季规则（固定 52、Mega 后 55、普通上限 + 挚友 + 2）**对所有 Mega 等级都生效，大师联盟也适用**。PvPoke 当前的做法不同：只有 Mega 等级 4 是 52，大师联盟仍是 50（`Pokemon.js` 第 294 行；`interface/PokeSelect.js` 第 347 行把 Mega 等级 4 的原形等级算作"Mega 等级 − 2"，说明它的 52 是"基础上限 50 + 2"）。

## 8. PvPoke 的 AI 策略

这一节是以后改进的重点，所以把假设写清楚。

PvPoke 有两套决策代码：
- `battle/actions/ActionLogic.js`：1v1 模拟用，完全确定性。排名、对战页面、矩阵都用它。
- `training/TrainingAI.js`：训练对战（3v3）用，带随机权重。换人只在这里。训练 AI 出招时最终也调用 `ActionLogic.decideAction`。

### 8.1 总的假设（最需要注意的）
1. **完全信息**：AI 知道对手的精确 HP、能量、招式、剩余盾数。
2. **防守方默认必开盾**：1v1 模拟里，只要还有盾就开，只有少数例外（见 8.2）。防守方不知道也不猜来的是哪个招式。
3. **因此骗盾必定成功**：攻方的"骗盾"逻辑建立在对手一定会开盾的基础上。
4. **攻方规划时不考虑对手会反击**：寻找最快击倒方案的搜索只看自己的能量和对手的 HP、盾，假设对手有盾就挡。
5. **只看 1v1**：模拟模式不考虑队伍里还有谁，不保留能量或盾给下一只。
6. **每只宝可梦有三个可调设置**（`Pokemon.js` 第 113–116 行）：
   - `baitShields`：0 不骗盾，1 选择性骗盾（默认），2 总是骗盾
   - `farmEnergy`：只用快招（默认关）
   - `optimizeMoveTiming`：优化出招时机（默认开）

### 8.2 什么时候开盾
来源：`Battle.js` `useMove` 第 1081–1262 行，`ActionLogic.wouldShield` 第 1164–1280 行。

默认：有盾就开。以下情况改用 `wouldShield` 的判断：
- 来的招式带"必定提升自己攻击"或"必定降低对手防御"的效果（如 Power-Up Punch、Acid Spray）。
- 防守方自己的最优大招会降低自己的防御（如 Close Combat）：
  - 攻方还有盾时，用 `wouldShield` 判断；
  - 攻方没盾时，只有当防守方的下一个大招周期能打倒攻方、且不会被攻方抢先时才用 `wouldShield`。
- 特定形态（盾形态坚盾剑怪、古月鸟的两个形态等）有专门规则。

`wouldShield` 的规则（满足任一条就开盾）：
1. 挨了这一下后的剩余 HP ≤ "周期伤害"。周期伤害 = (攻方攒下一个同样大招所需的快招数 + 1) × 快招伤害 + 1，再乘以防守方盾数。
2. 攻方**任意一个**大招（不管现在能量够不够）的伤害 ≥ 防守方当前 HP / 1.4，且攻方快招每回合伤害 > 1.5。
3. 攻方任意一个大招的伤害 ≥ 防守方当前 HP − 周期伤害。
4. 来的招式会降低攻方自己的攻击（如 Superpower），且伤害超过防守方当前 HP 的 55%。
5. 攻方设置为"总是骗盾"（`baitShields == 2`）时，直接返回"会开盾"。

注意第 2、3 条里有一个条件 `attacker.energy + chargedMove.energy >= chargedMove.energy`，它恒为真，所以实际上没有检查能量。这可能是 PvPoke 的笔误。

### 8.3 怎么决定放哪个大招、什么时候放
来源：`ActionLogic.decideAction`，第 6–1042 行。每当宝可梦可以行动（冷却为 0）时调用一次，返回大招或"用快招"。按顺序判断，前面命中就不往后走：

**第 0 步**：能量不够最便宜的大招，或设置了只用快招 → 快招。

**第 1 步：快死了就把能放的放掉**（第 38–208 行）
- 估算"还能活几回合"：假设对手照常出快招，我有盾时对手用最便宜的大招骗盾，我没盾时对手用任何能打倒我的大招。
- 如果活不到下一个快招打完（细分为几种情况，考虑 CMP 和对手快招时长）→ 放当前能放的伤害最高的大招。如果赢 CMP 且能量够同一个招放两次、两次总伤害更高，则选它。

**第 2 步：能直接打倒就打**（第 212–234 行）
- 对手没盾，某个大招能打倒对手，且这个招不会削弱自己 → 放。
- 但如果对手的 HP 低到一个快招就能打倒，则不放大招，用快招收掉。
- 设置了骗盾时，只考虑最便宜的那个招。

**第 3 步：特定宝可梦的规则**（谜拟Q、小陨星、古月鸟），略。

**第 4 步：优化出招时机**（第 267–373 行）
- 目的：让大招在对手快招刚打完的时候放，避免对手白拿回合。
- 做法：如果对手当前冷却为 0 或大于目标值（一般 500ms），就再打一个快招等一等。
- 不等的情况：双方快招时长相同；自己的快招时长是对手的整数倍；等的话能量会溢出 100；等的话会被打倒；现在就能打倒对手。

**第 5 步：对手还很耐打时，直接选"最优招"**（第 400–447 行）
- 条件：对手 HP / (最优大招伤害 + 攒它期间的快招伤害) > 2。
- "最优招"（`bestChargedMove`）主要按每点能量伤害（DPE）选，带一批针对具体招式的修正（`Pokemon.js` `resetMoves`，第 711–878 行）。
- 骗盾：如果设置了骗盾、对手有盾、且对手会对我的某个招开盾 → 改放最便宜的招。
- 选中的招会削弱自己时，先攒到接近 100 能量再连放。

**第 6 步：对手快倒了，搜索最快的击倒方案**（第 449–812 行）
- 状态：自己的能量、对手 HP、回合数、对手盾数、已用招式、攻击等级变化。
- 假设：对手有盾就挡（伤害记 1，盾数减 1）；每个大招占 1 回合（**没有按新系统改成 2 回合**）；概率性效果不计。
- 找到回合数最少的方案，取方案里的第一个招。

**第 7 步：对方案做一串修正**（第 814–1002 行）
- **骗盾**（设置了骗盾、对手有盾、自己有两个以上大招）：
  - 如果有一个更贵、DPE 更高的招现在能量还不够 → 先不放，继续用快招攒能量。攒够贵招的能量后，实际放的往往仍是便宜的那个。这就是 PvPoke 的"骗盾"：攒到对手无法从能量判断来的是哪个招，再用便宜招换盾。
  - 例外：便宜招本身必定提升攻击，且贵招的 DPE 不超过它的 1.5 倍 → 不骗。
  - 如果能量已经够贵招、贵招 DPE 超过 1.5 倍、且按 `wouldShield` 对手不会挡 → 直接放贵招。
- 不骗盾，或对手没盾且没有削弱自己的招 → 按伤害从高到低放。
- 之后是 6 条左右的"补丁"规则（代码里自己叫 bandaid），在能量相近时偏好 DPE 更高的、不削弱自己的、或必定提升自己的招。
- 会削弱自己的招：尽量攒到能连放再用；自己没盾且对手马上要放大招时，推迟到对手放完之后。

### 8.4 什么时候换人
只在训练对战里，来源：`TrainingAI.js` `evaluateMatchup`（第 633 行）、`decideAction`（第 1030 行）、`decideSwitch`（第 1131 行）。

**评估当前对位**：把当前这对宝可梦以当前的 HP、能量拿去跑 1v1 模拟，跑四种情形（双方骗盾 / 双方不骗 / 不骗 / 自己只攒能量），每种情形遍历双方各种盾数组合，按权重 [4, 4, 1]（对应 0、1、2 盾）加权平均，得到 0–1000 的评分，500 是平手。

**是否换人**（带随机）：
- 条件：有换人策略、换人计时器为 0、还有别的宝可梦。
- 换人权重 = (500 − 评分) / 10，评分越差越想换。高难度 AI 在对手还有多只时门槛降到 450。
- 对手被换人计时器锁住（剩余超过 30 秒）、且自己有更克制它的宝可梦时，加权重。
- 自己 HP ≤ 25% 时不换（高难度）。
- 高难度 AI 还有"攒完能量再换"：继续打快招，等到对手快要有威胁的大招时再换。
- 然后在"换人 / 默认 / 骗盾 / 攒能量"几个选项里**按权重随机抽一个**。

**换谁上**（带随机）：
- 对每个候选跑上面的 1v1 评估。
- 评分 < 500：权重很小。
- 评分 ≥ 500：对手被锁住时偏好评分最高的（硬克制）；对手没被锁时偏好评分略高于 500 的（软克制，留余地应对对手反换）。
- 按权重随机抽。

**训练 AI 的开盾**（`decideShield`，第 1181 行）：不同于 1v1 模拟的"必开盾"。它先猜对手放的是哪个招（低难度 AI 会给对手能量加随机误差），再综合伤害占比、当前对位好坏、是否最后一只、是否被锁住等算出开和不开的权重，随机抽。

### 8.5 小结：我们要改进的点
- 1v1 模拟里的开盾几乎是"必开"，骗盾因此必定成功。结果对这个假设很敏感，但界面上看不出来。
- 换人和训练模式的开盾都是加权随机，同一局面每次结果不同，无法复现，也无法解释。
- 3v3 没有真正的前瞻：换人只看"当前这只对对面这只"的 1v1 评分，不考虑后续对位、能量和盾的保留。
- 出招搜索还按"大招占 1 回合"算，和 PvPoke 自己更新后的时序（2 回合）不一致。
- 大量规则是针对具体宝可梦或招式的补丁（Registeel、Melmetal 对 Cresselia、Superpower、Obstruct 等），不通用。

### 8.6 简单规则策略与 PvPoke AI 的比较（第 3c 步）
`pogo_sim/simple_policy.py` 是一个刻意简单的基准策略：8 条按顺序判断的出招规则 + 3 种开盾方式，每条都能单独开关或调参，每个决定都写原因进时间线。规则见该文件开头。

用 3b 的 52 场对局（同样的宝可梦、等级、IV、招式、盾数），双方都换成简单规则策略再跑一遍，和 PvPoke AI 的结果比较（`tools/compare_simple_policy.py` 生成 `docs/simple_policy_vs_pvpoke.md`）。引擎已逐回合一致，所以差异全部来自决策。

| 配置 | 胜负与 PvPoke 相同 | 大招序列完全相同 | 评分平均差（满分 1000） |
|---|---|---|---|
| 默认：骗盾 + 出招时机 + 总是开盾 | 49/52 | 16/52 | 38 |
| 不骗盾 | 48/52 | 18/52 | 46 |
| 不优化出招时机 | 51/52 | 13/52 | 25 |
| HP 会低于 50% 才开盾 | 49/52 | 13/52 | 45 |
| 能放就放（最便宜的招） | 47/52 | 5/52 | 72 |

胜负不同的 3 场，原因各是一类决策：
1. **出招时机**（Galvantula vs Azumarill 1-1）：我们要等对手快招"本回合结束"（冷却 1）才放，Galvantula 等了两次，第 21 回合才放 Discharge。PvPoke 对 4 回合以上的长快招放宽到冷却 ≤ 2，第 17 回合就放了。
2. **骗盾**（Mamoswine vs Altaria 1-1）：Avalanche 和 Ancient Power 都是 45 能量。PvPoke 先把弱的 Ancient Power 扔进盾里；我们的骗盾只看"更便宜"的招，于是把 Avalanche 扔进了盾。
3. **选招**（Dewgong vs Swampert 1-1）：PvPoke 选 Icy Wind（必定降对手攻击，被挡也生效）；我们按每点能量伤害选了 Drill Run，完全没考虑能力变化的价值。

其他常见差异（不影响胜负，但影响评分）：
- **开盾例外**：PvPoke 不挡早期的 Power-Up Punch 这类"必定提升自己"的招；自己的主力招会降自己防御时（如 Skarmory 的 Brave Bird）也常不挡（见 8.2）。我们默认总是挡。
- **选招偏好**：PvPoke 有一批按招式的补丁规则（8.3 第 7 步），例如 Altaria 先放 Moonblast 而不是 DPE 更高的 Sky Attack、Obstagoon 先放 Obstruct、Registeel 先放 Zap Cannon。
- **快被打倒时的判断**：PvPoke 推算"还能活几回合"，我们只看对手下一个快招或现成的大招，有时早一回合或晚一回合。

值得注意：关掉我们的"出招时机"规则，胜负和评分反而更接近 PvPoke（51/52、平均差 25）。说明 PvPoke 的时机规则和我们的差别比较大（它有更多例外条件，长快招的窗口也更宽），而"出招时机"对结果的影响不小。

可以考虑的改进（还没做，等用户决定）：
- 骗盾时也考虑"能量相同但伤害更低"的招；
- 选招时给必定生效的能力变化（Icy Wind、Lunge、Power-Up Punch、Obstruct 等）一个价值；
- 出招时机对长快招放宽窗口，或者改成 PvPoke 的条件；
- 开盾加入"不挡必定提升自己的招"之类的例外，做成开关。

## 10. 自定义数据（覆盖文件）

未发布的宝可梦、招式，以及对已有条目的修正，写在 `data/custom/` 下的 TOML 文件里，不改 `data/gamemaster.json`。实现在 `pogo_sim/custom.py`。

```python
gm = load_gamemaster(custom_files=["data/custom/mega_froslass.toml"])
print("\n".join(gm.custom_log))  # 每条改动一行，包括种族值怎么换算来的
```

### 10.1 格式
- **TOML**：Python 标准库 `tomllib` 能读，不加依赖；能写注释，可以写明数据来源和哪些是假设。
- **字段名与 gamemaster.json 相同**（`speciesName`、`baseStats`、`fastMoves`、`energyGain`……），PvPoke 的条目可以直接复制过来改。合并发生在原始字典这一层，合并后和 gamemaster 走同一套解析。
- 四种表，写法 `[表名.ID]`，按这个顺序应用（先招式后宝可梦，宝可梦可以用同一个文件里新加的招式）：

  | 表 | 作用 | 报错 |
  |---|---|---|
  | `new_moves` | 新招式 | ID 已存在 |
  | `patch_moves` | 修改已有招式，只替换写出来的字段 | ID 不存在 |
  | `new_pokemon` | 新宝可梦 | ID 已存在 |
  | `patch_pokemon` | 修改已有宝可梦，只替换写出来的字段 | ID 不存在 |

  "新"的 ID 撞上已有条目，多半是 PvPoke 后来加了同名条目，要人来决定删掉自定义还是改成 patch；"改"的 ID 不存在，多半是拼错。两种都不悄悄继续。
- patch 是顶层字段整体替换：列表和 `baseStats` 这类嵌套值整个换掉，不做合并。
- 另有 `[meta]` 表放说明（`description`、`sources`），加载时不用。
- 多个文件按给定顺序应用，后面的文件可以修改前面文件新加的条目。

### 10.2 种族值
新宝可梦二选一：
- `baseStats = { atk, def, hp }`：直接给 GO 种族值。
- `mainSeriesStats = { hp, attack, defense, spAttack, spDefense, speed }`：给正作六项，加载时按 2.5 节换算。`tags` 里有 `"mega"` 时用 Mega 的削弱规则（≥ 6000 乘 0.97），否则用非 Mega 的（≥ 4000 乘 0.91）。两条规则可以在 `load_gamemaster` 里换成别的假设。

`patch_pokemon` 也可以写 `mainSeriesStats`，换算结果替换原来的 `baseStats`。

### 10.3 检查
加载时会报错的情况：表名或字段名不认识（字段名以 gamemaster 里出现过的为准）、缺必填字段、属性名不认识、种族值没写全、`speciesId` / `moveId` 和表名里的 ID 不一致、招式数值不是数字；新增或修改过的宝可梦引用了不存在的招式，或快招列表里有大招、大招列表里有快招。

必填字段：
- 新招式：`name`、`type`、`power`、`energy`、`energyGain`、`turns`。快招还是大招按 PvPoke 的规则判断（`energyGain > 0` 是快招，除非写了 `category`）。
- 新宝可梦：`speciesName`、`dex`、`types`、`fastMoves`、`chargedMoves`，以及 `baseStats` / `mainSeriesStats` 之一。`tags`、`extraChargedMoves`、`defaultIVs` 可省略；`released` 不写时为未发布。
